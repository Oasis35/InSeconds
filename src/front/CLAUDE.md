# CLAUDE.md — front

Front d'InSeconds (`src/front`), en prod et sur le staging. Vue d'ensemble, conventions et pièges : [`CLAUDE.md`](../../CLAUDE.md) racine. Ce fichier détaille le code tel qu'il est ; toute PR qui change le front le met à jour.

État : les domaines `account` (connexion, profil, appareils, confirmation d'email), `admin` (tableau de bord, défis, pool, joueurs, actions), `gameplay` (la manche d'un morceau) et `daily` (le jeu du jour : accueil, reprise, manche, récap, « déjà joué », série et gels) existent ; `/privacy` est la page de confidentialité et mentions légales. L'admin a ses cinq onglets (tableau de bord, défis, pool, joueurs, actions). CSP en observation (`report-only`) en prod et au staging (#300, § PWA et nouvelle version). Le mode Run (domaine `runs`) est conçu mais pas codé ([`docs/runs/`](../../docs/runs/README.md)).

## Commandes

```bash
cd src/front/InSeconds.Client
npm ci
npm start                 # http://localhost:5176, /api /health /jobs relayés vers l'API (:5175, proxy.conf.json)
npm run build             # build de prod (service worker compris)
npx ng test --watch=false # Vitest en mode navigateur (Chromium)
npm run lint:arch         # Sheriff + couche domain/ sans Angular
npm run generate-api      # régénère les clients NSwag (cf. « Clients de l'API »)
```

- Angular CLI 22.2 exige **Node ≥ 22.22.3** (ou 24.15+). La CI prend le dernier Node 22.
- Chromium déjà installé ailleurs (environnement sans `playwright install`) : `PLAYWRIGHT_CHROMIUM_PATH=/chemin/vers/chromium npx ng test --watch=false`.
- Clients de l'API : cf. § Clients de l'API. E2E : cf. § E2E.

## Stack

Angular 22 standalone, **zoneless**, signals, Tailwind v4 + tokens `:root` de la DA dans `styles.scss`, ngx-translate, Vitest navigateur, plus :
- **NgRx SignalStore** (`@ngrx/signals`) pour les stores ;
- **CDK Dialog** (`@angular/cdk`) pour les modales et panneaux bas ;
- **service worker Angular** (`@angular/service-worker`) : PWA et détection de nouvelle version ;
- **Sheriff** (`@softarc/sheriff-core`) pour les frontières entre dossiers.

Angular, CDK, NgRx, ngx-translate, Tailwind, Vitest et Sheriff sont épinglés à une version exacte dans `package.json`, `@angular/*` alignés (piège 15 racine).

## Frontières (Sheriff)

`npm run lint:arch` (job CI `front`) fait échouer la CI si :
- `ui` importe autre chose que `ui` ;
- `core` importe un domaine ;
- une autre couche que `data-access` importe `api/` ;
- `gameplay` importe un mode, ou `daily` et `runs` s'importent mutuellement ;
- `domain/` importe Angular, NgRx, RxJS ou ngx-translate (`scripts/check-pure-domain.mjs`, Sheriff ne voit pas les bibliothèques).

Sheriff ne vérifie que les fichiers atteignables depuis `src/main.ts` (routes chargées à la demande comprises) : tous les domaines étant routés, `npm run lint:arch` n'a plus besoin d'entrées supplémentaires. Ajouter un domaine : rien à changer, les dossiers `src/app/<domaine>/<couche>` sont déjà déclarés dans `sheriff.config.ts` ; un nouveau domaine qui peut en importer un autre s'ajoute à `DOMAIN_DEPENDENCIES` (`daily` : `gameplay` et `account`, ce dernier pour `SessionLoader`, qui crée l'invité avant la première partie ; `admin` : `account` et `gameplay`, ce dernier pour l'histogramme « en combien de temps les autres ont trouvé »). Une couche `feature/` n'importe ni `api/` ni `environment/` : l'adresse de l'API passe par la couche `data-access` (`provideDailyApi`).

## Routes

- `/` → `/daily` (tant que le mode Runs n'est pas public).
- Anciennes adresses redirigées : `/blindtest` → `/daily`, `/login` → `/account/login`, `/login/verify` → `/account/login/verify`, `/profile` → `/account/profile`, `/profile/confirm-email` → `/account/confirm-email`, `/confidentialite`, `/mentions-legales`, `/legal-notice` → `/privacy`.
- **Toutes les redirections gardent la query string et le fragment** (`redirectKeepingQuery`) : lien magique, confirmation d'email, `from=legacy`. Testé dans `app.routes.spec.ts`.
- `/account/**` : domaine `account` (chargé à la demande). `/admin/**` : domaine `admin` (`/admin` → `/admin/dashboard`, l'ancien `/admin/pool` et `/admin?tab=pool` aussi, page de la grille et autres paramètres gardés). `/daily` : domaine `daily` (`DAILY_ROUTES`, avec `provideGameplay()` : le lecteur ne se charge qu'avec cette route). `/privacy` : page de confidentialité (`core/shell/privacy`). Tout le reste : 404.

## Erreurs

- L'API renvoie un `ProblemDetails` avec `code` (stable, `module.raison`) et `traceId`. `toAppError()` le convertit en `AppError { code, status, traceId }` (erreur `HttpClient`, `ApiException` ou `ProblemDetails` levés par un client NSwag, corps JSON ou Blob ; `common.network` sans réponse, `common.unexpected` sans code lisible).
- `ERROR_MESSAGE_KEYS` (`core/errors/error-messages.ts`) est **la seule table** qui traduit un code en clé i18n. Un code inconnu → `errors.common.unknown`, affiché avec le `traceId` (`<app-error-message>`). Un module ajoute ses codes dans cette table et leurs traductions ; `translations.spec.ts` vérifie que chaque clé existe en FR et en EN. Les codes `admin.*` y sont aussi (`errors.admin.*`, #318). Seules adaptations locales, sur un code déjà dans la table : le recalcul des stats d'un défi lit `common.not_found` comme « aucun défi pour ce jour », et le témoin de la génération reconnaît `admin.pool_insufficient` pour afficher son propre message, daté.
- Remontée des erreurs vers `POST /api/client-errors` (`ErrorReportingService`, `GlobalErrorHandler`, intercepteur des 5xx et échecs réseau, jamais de query string). Chaque envoi ajoute `appVersion` (`DEPLOYED_AT`, `null` hors image Docker) et `online` (`navigator.onLine`) ; l'appareil est déduit par l'API du `User-Agent` (cf. `src/back/CLAUDE.md`).
- **Échec de lecture d'un extrait** (permanent) : `AudioError: <chargement|lecture>, <cause>` (`HtmlAudioPort`, `describeAudioError`), envoyé par la même remontée en `source: 'js'` à chaque erreur du lecteur pendant un palier : `chargement` pour l'événement `error` de l'élément (cause : le code `MediaError`, `MEDIA_ERR_SRC_NOT_SUPPORTED` pour une adresse que le CDN refuse, suivi de la réponse du CDN : `probePreview` redemande un octet de l'extrait par `fetch` et ajoute `, HTTP 403 (text/html)` ou `, HTTP injoignable (TypeError)`, l'élément audio ne donnant jamais le statut HTTP), `lecture` pour un `play()` rejeté (cause : le nom de l'exception, `NotAllowedError`…). Jamais l'adresse de l'extrait ni le texte du navigateur. Sert à distinguer, dans Grafana, un extrait retiré ou expiré d'un son bloqué par l'appareil.
- **Diagnostics de la recette iPhone** (#233, 15/10/2026 : page zoomée à chaque page, son qui coupe), envoyés par la même remontée en `source: 'js'`, sans rien changer au jeu. À retirer une fois les causes trouvées (`docs/taches.md`) :
  - `Viewport: <chemin> zoom ×…, écran … px, page … px, focus …[, plus large : …]` (`core/diagnostics/viewport-reporter.ts`, `provideViewportReporting()`) : mesuré une seconde après chaque navigation et à chaque redimensionnement de `visualViewport`, envoyé seulement si la page est zoomée (`visualViewport.scale` > 1,05) ou plus large que l'écran, trois fois au plus par chargement. Le focus ne donne que la balise et le type du champ, jamais sa valeur.
  - `AudioStall: palier … s, premier son après … ms, … coupure(s)` (`HtmlAudioPort`, `describeStall`) : à la fin d'un palier, si le premier son a mis plus de 1,5 s à sortir ou si le son s'est coupé en route (`waiting` après le premier son). Jamais l'adresse de l'extrait ; rien pour une lecture arrêtée avant la fin ni pour l'extrait entier.

## Stores

`withRequestStatus()` (`core/store/`) : état `idle | pending | fulfilled | { error: AppError }` et `isPending`/`isFulfilled`/`error`. Dans un store : `patchState(store, setPending())`, puis `setFulfilled()` ou `setError(await toAppError(e))`. État protégé (option par défaut de SignalStore) : on ne le modifie que par les méthodes du store. `SessionStore` (joueur courant : id, pseudo, email, invité ou compte, admin) est rempli par `account`. Piège : un nom d'état ne doit pas être celui d'une méthode du même store (`logout` état et méthode se masquaient) — d'où `…Status` pour les états.

## PWA et nouvelle version

- `provideServiceWorker('ngsw-worker.js')`, désactivé en dev. `ngsw-config.json` met en cache les fichiers du front (JS, CSS, index, traductions, icônes), jamais l'API (**aucun `dataGroups`**, S10), et exclut `/jobs` des navigations.
- `VersionService` : une nouvelle version prête (`VERSION_READY`) est **appliquée toute seule** (rechargement de la page) au premier moment sûr, sans rien demander au joueur (décision de Clément du 12/10/2026, bonne pratique web.dev / Angular : jamais sous les doigts du joueur). Chaque page déclare quand elle l'accepte avec `allowReload(() => moment, destroyRef)` : `now` (tout de suite), `background` (onglet passé en arrière-plan) ou `navigation` (seulement au prochain changement de page) ; le plus prudent des moments déclarés l'emporte, une page qui ne dit rien vaut `navigation` (compte, admin). Un changement de page applique toujours la mise à jour, jamais avec une fenêtre ouverte (CDK `Dialog`) ; une navigation qui ne change que la query string ou le fragment (`?page=` du pool admin) n'est pas un changement de page (#318). Page du jeu (`daily/feature/reload-moment.ts`) : `now` sur accueil, reprise, « déjà joué », pas de défi, erreur ; `background` sur le récap et le chargement ; `navigation` en pleine manche (`playing`). Confidentialité : `now`. Garde-fou anti-boucle : un second rechargement automatique moins d'une minute après le précédent (`sessionStorage`) n'a pas lieu, le bandeau « Nouvelle version disponible, Recharger / Plus tard » (`<app-update-prompt>`) s'affiche à la place. Ce bandeau ne sert plus qu'en secours : état irrécupérable du service worker, qui met aussi la mise à jour en attente du prochain moment sûr. Vérification au démarrage (sans elle, la nouvelle version n'était vue qu'environ 25 s après l'ouverture, le service worker attendant un moment sans requête pour vérifier) et au retour de l'onglet au premier plan. **Remplacement du service worker lui-même** (son script change avec Angular ou avec la CSP, piège 49) : le navigateur installe le nouveau en arrière-plan pendant la visite, et la page reste servie par l'ancien jusqu'à l'événement `controllerchange` ; ce changement est traité comme une nouvelle version (même moment sûr), sinon une partie lancée avant restait sur l'ancien worker. Le premier worker d'une première visite n'en est pas un. La mise à jour du worker est demandée au démarrage et au retour au premier plan (`registration.update()`, jeton `SERVICE_WORKER_CONTAINER`). Tests : `version.service.spec.ts`.
- **Le worker garde la CSP de son installation** (piège 49 racine) : le worker redemande par `fetch` tout ce que la page charge (extraits, pochettes, polices), sous la CSP reçue avec son script : toute origine tierce va donc aussi en `connect-src`. `Dockerfile.prod` ajoute `// CSP <empreinte>` à la fin de `ngsw-worker.js`, qui change donc avec la CSP et se réinstalle chez les joueurs. Vérifié par `scripts/check-nginx-headers.sh`.
- **Désactiver le service worker chez tous les joueurs** (bug grave) : `safety-worker.js` est copié à la racine du build. Le servir à la place de `ngsw-worker.js` (et `worker-basic.min.js`) — par exemple un `location = /ngsw-worker.js { alias …/safety-worker.js; }` dans nginx — désinscrit le service worker et vide ses caches au prochain passage du joueur.
- **Content-Security-Policy (S14)** : `nginx/csp.conf.template`, transformé au build par `Dockerfile.prod` (arguments `CSP_MODE` = `report-only` (défaut) ou `enforce`, `CSP_API_ORIGIN` = origine de l'API de l'environnement) en `csp.conf`, inclus par `security-headers.conf` donc sur chaque `location`. En `report-only` l'en-tête est `Content-Security-Policy-Report-Only` : rien n'est bloqué, le navigateur déclenche `securitypolicyviolation`, que `core/errors/csp-violation-reporter.ts` (`provideCspViolationReporting()`) envoie à `POST /api/client-errors` avec `source: 'csp'` (message `CSP (report|enforce) <directive> bloque <ressource>`, ressource et source sans query string). Origines : `'self'`, l'API (`connect-src`), `*.dzcdn.net` (extraits en `media-src`, lus par l'élément audio, pochettes en `img-src`, et en `connect-src` pour la sonde d'un extrait illisible, `probePreview`), Google Fonts (aussi en `connect-src` : le service worker redemande les polices par `fetch`, sous sa propre CSP, piège 49), `blob:` (silence du déverrouillage audio) / `data:` (images) ; aucun script en ligne (`script-src 'self'`) : **`inlineCritical: false`** dans `angular.json` (production et staging), car l'inlining du CSS critique d'Angular ajoute un `onload=` sur la feuille de style, que `script-src 'self'` refuserait. `style-src 'unsafe-inline'` reste (styles des composants). **En observation (`report-only`) en prod et au staging**, le temps d'écarter la CSP des échecs de lecture d'extraits sur Android (#300) : `docker-compose.prod.yml` et `docker-compose.staging.yml` fixent `CSP_MODE` (pas lu dans `.env.prod`), `enforce` la rend bloquante. Le défaut du `Dockerfile.prod` reste `report-only` (image construite sans argument, celle du job CI `nginx-headers`). Pour essayer une politique modifiée sans rien casser : `CSP_MODE=report-only` le temps de l'observation, violations dans Grafana (`source` = `csp`, tuile « Violations CSP » du tableau Exploitation). Vérifié par `scripts/check-nginx-headers.sh`.
- Image de prod : `Dockerfile.prod` (nginx, args `BUILD_CONFIGURATION` `production`/`staging` et `BUILD_TIME`, l'heure de déploiement de l'admin : `ng build --define`, cf. § Domaine admin), `nginx/nginx.conf` + `nginx/security-headers.conf` (en-têtes de sécurité inclus dans chaque `location`). Cache immuable des bundles hashés, `no-cache` pour l'index et les traductions, redirection `code.run` → `from=legacy`, et une `location` regex **déclarée avant celle des `.js`** qui sert `ngsw.json`, `ngsw-worker.js`, `safety-worker.js`, `worker-basic.min.js` et `manifest.webmanifest` en `no-cache` (sinon `ngsw-worker.js` prendrait le cache immuable des bundles). Vérifié par `scripts/check-nginx-headers.sh` (job CI `nginx-headers`) : en-têtes de cache et de sécurité, types MIME, `ngsw.json` servi sans aucun `dataGroups` (S10), et redirection de l'ancienne adresse `code.run` (301 vers `https://inseconds.cc`, chemin et query gardés, `from=legacy` ajouté), que les E2E ne voient pas (ils tournent sur `ng serve`, sans nginx). Servie aussi sur le staging (`docker-compose.staging.yml`, configuration `staging` : API `https://api-dev.inseconds.cc`, appelée avec CORS et cookie).

## E2E

**31 specs Playwright, 126 tests** (`e2e/specs/`, page objects dans `e2e/pages/`, fixtures dans `e2e/fixtures/`), joués contre l'hôte de test (`InSeconds.Api.Testing`, faux Deezer, faux email, routes `/api/e2e/*`). Ports : API de test sur **5175** en CI / **5177** en local, front sur **5176** en CI / **5178** en local (configurations `ng serve` `e2e-ci`/`e2e`, `proxy.e2e*.conf.json`, `environment.e2e.ts`). `serviceWorkers: 'block'` dans `playwright.config.ts` (E12). En local, `playwright.config.ts` démarre l'hôte de test (avec `--no-launch-profile`, sinon `launchSettings.json` impose `Development`, piège 9) et `ng serve` ; la base E2E se passe par `E2E_DB_CONNECTION` (chaîne de connexion complète, jamais commitée — Sonar S2068). Le job CI `e2e` les lance tous ; aucune liste de specs désactivés, aucun `test.fixme`.

- **Fixtures** : les boucles d'étapes séquentielles des fixtures et page objects passent par `inSequence`/`times` (`e2e/fixtures/sequence.ts`, Sonar S9382 : pas d'`await` dans une boucle).
- **Données** : `api.reset()` **re-sème le pool** (l'hôte de test vide tout, puis `reseed`), sauf `reset({ emptyPool: true })` (tout vidé : aucun défi possible) et `reset({ deleteChallenge: true })` (le défi du jour seul est retiré, `POST /api/e2e/delete-challenge`). Les parties de l'API se jouent par position (`startGame`, `submitEmptyAnswers`). La fixture `api-client.ts` lit les liens dans le dernier email capturé (`/api/e2e/last-email`) et attend un lien différent du précédent : l'email part de l'outbox, après la réponse 204. `error-reporting.spec.ts` provoque une erreur de l'API par `GET /api/e2e/throw`.
- **Son** : l'extrait du faux Deezer est `/test-audio.mp3`, servi par le front de test (`E2E_FRONT_PORT`, 5176 par défaut = CI ; `playwright.config.ts` pose 5178 en local) : sans lui, le son ne se charge pas. Le fichier vit dans `e2e/public/` et seule la configuration de build `e2e` le copie : il n'est pas dans l'image de prod (#318, vérifié par `scripts/check-nginx-headers.sh`). Les paliers se jouent en temps réel (le lecteur s'arrête sur la position de l'extrait) : `playStep` attend la durée du palier, la suite d'un palier se lit au chrono du lecteur (`data-testid="round-timer"` : « … » au chargement, « 0.0s / 0.5s » en lecture, « 0.5s / 0.5s » palier joué) plutôt qu'à une attente fixe, et le test du score qui écoute jusqu'à 10 s est marqué `test.slow()`. Les suggestions sont des `role="option"`.
- **Admin** (`admin.spec.ts`) : l'admin se connecte par `POST /api/e2e/login-as-admin`, les données viennent de `POST /api/e2e/reseed` (cf. `src/back/CLAUDE.md`, « Hôte de test »). « Liste les comptes inscrits » se connecte par `linkAccount` et vérifie le badge « Admin » du compte `AdminE2E` ; le chip « toi » des défis montre donc ce pseudo (l'invité qui a joué devient ce compte) ; « liste les défis existants » compte les défis du mois par `AdminPage.apiGetChallengeDates` (le seed écrit aussi des défis à J-5, J-15, J-30…). Chaque onglet ne charge ses données qu'à son ouverture (vérifié).
- **Autres specs à connaître** : `sound-on-click.spec.ts` (le son ne part que d'un clic), `mobile-input-zoom.spec.ts` (profil iPhone 13 : champ de réponse en 16 px, page qui ne déborde pas), `thanks-notice.spec.ts` (message de remerciement du lancement), `account-data.spec.ts` (« Tes données » du profil : téléchargement du JSON, suppression du compte par la fenêtre où l'on retape son pseudo, annulation), `devices.spec.ts` (appareils connectés : liste repliée à l'arrivée, déconnexion d'un appareil, « déconnecter les autres », avec deux contextes de navigateur, aides `openOtherDevice` et `signInAgain` de `login.page.ts`), `legacy-urls.spec.ts` (redirections des anciennes adresses avec leur query string, `/profile` d'un compte connecté, avis `from=legacy` qui ne revient pas au rechargement), et, dans `profile.spec.ts`, le lien de compte qui disparaît pendant la manche (#318).

## Clients de l'API (NSwag)

Un client par module, dans `src/app/api/<module>/api.generated.ts` (**fichier généré, commité**, exclu de Sonar sous ce nom). Il est généré depuis le document OpenAPI du module, servi **par l'hôte de test seulement** (`/openapi/<module>.json`) et sauvegardé dans `src/back/InSeconds.Api.Testing/openapi/<module>.json` (cf. `src/back/CLAUDE.md`) :

```bash
cd src/front/InSeconds.Client
npm run generate-api      # lit le document sauvegardé ; nswag/<module>.nswag.json fixe la sortie
```

Après tout changement d'endpoint d'un module : régénérer le document côté back (cf. `src/back/CLAUDE.md`), puis le client ici, et commiter les deux. Un nouveau module ajoute son `nswag/<module>.nswag.json` (nom du jeton `<MODULE>_API_BASE_URL`, `SingleClientFromOperationId`) et sa ligne dans le script `generate-api`. Le client n'est utilisé que par l'adaptateur de la couche `data-access` du domaine (`PlayersApi`), qui rend des types du domaine : le JSON livre les dates en texte alors que le client les annonce en `Date`, l'adaptateur les convertit ; un `204` (`GET /api/players/me` sans identité) est levé par le client comme une erreur, l'adaptateur le traduit en `null`.

## Domaine gameplay

`src/app/gameplay/`, quatre couches. La manche d'un morceau (écouter, répondre, voir la réponse), partagée par Daily et plus tard Runs ; elle ne connaît aucun mode (Sheriff : `gameplay` n'importe aucun mode).

Le mode fournit une `ListenPolicy` (paliers, prolongeable ou non) et une `HintPolicy` (seuils de déblocage, les réglages du back) ; la manche rend un `RoundSubmission` (palier annoncé, `wasExtended`, artiste, titre) à envoyer. `answer.ts` (saisie libre coupée au premier « - », navigation en boucle dans les propositions), `round-result.ts` (ce que le serveur révèle, **sans les points** : ils sont au mode), `hint-label.ts` ;

- `feature/` : `TrackRoundComponent` (`app-track-round`, lecteur + indices + saisie + confirmations + révélation ; il **injecte** le `TrackRoundStore` du mode et fournit lui-même son `AnswerSearchStore`), `provideGameplay()` ;
- `ui/` : `RoundPlayerComponent` (chrono, barre avec un repère par palier, ↺, « ▶ Xs », erreur de lecture, pas d'extrait), `AnswerInputComponent` (champ, ✕, liste, clavier), `HintPanelComponent`, `RevealCardComponent`, `GuessTimeChartComponent`, tous présentationnels.

Règles :
- **Le mode pilote, la manche ne connaît ni le réseau ni les points.** Le mode appelle `store.start(config, extraitSuivant)`, écoute `answered` (le `RoundSubmission`), envoie la réponse puis appelle `store.reveal()` et passe le `result` à `<app-track-round>` — ou `store.submissionFailed()`. Pour un indice, `hintRequested(niveau)` part, le mode interroge le back puis appelle `store.applyHints(niveau, indices)`. Il projette ses éléments dans `[roundActions]`, `[roundBadge]`, `[roundScore]` et `[roundNext]`.
- **Le mode envoie l'écoute au serveur** (`PATCH …/listening`) à chaque changement de `chosenSeconds` du store : le serveur débloque les indices (sinon 409) et pose le plancher anti-triche (piège 35) d'après ce palier. La manche ne le fait pas elle-même (pas de réseau).
- **Premier échec de lecture d'un morceau : relance automatique.** Si la `RoundConfig` fournit `refreshPreviewUrl`, la manche redemande seule une adresse fraîche et relance le palier choisi, sans afficher d'erreur (`recoverFromAudioError`, appelé par l'`effect` qui suit le lecteur) : les adresses Deezer expirent au bout de 15 min (piège 14), un joueur qui a pris son temps tombe sur une adresse morte. **Une seule fois par morceau** : un second échec affiche « Réessayer / Passer » (jamais de boucle, piège 33). Pas de déverrouillage (hors d'un clic) : le son l'a été au clic qui a lancé le morceau.
- **« Réessayer » après un échec de lecture** déverrouille d'abord le son dans le clic (`unlock()`, la relance partant après l'appel réseau, iPhone, #313), puis recharge l'extrait ; si la `RoundConfig` fournit `refreshPreviewUrl`, depuis une adresse fraîche (signature Deezer expirée, piège 14). Une réponse qui arrive après la fin de la manche est ignorée.
- **Extrait retiré en cours de journée** : `refreshPreviewUrl` rend `null` quand le mode n'a plus d'extrait pour le morceau (Deezer l'a retiré depuis le début de la partie : le back renvoie une adresse vide). La manche passe alors en `no-preview` (« Aperçu non disponible », bouton « Passer » sans confirmation, `previewWithdrawn`) au lieu de relancer l'adresse morte, que « Réessayer » rechargeait sans fin. Un échec de la redemande (réseau, partie finie ailleurs : Daily lève une erreur) garde l'adresse. Tests : `track-round.spec.ts`, `track-round.store.spec.ts`, `daily-game.store.spec.ts`.
- **Fourni par la route du mode** : `provideGameplay()` (lecteur, autocomplete, adresse de l'API du catalogue) est dans les `providers` de la route Daily (`DAILY_ROUTES`), pas dans `app.config.ts` : le lecteur reste ainsi dans le morceau chargé à la demande.
- **L'`AudioPort`** : `load(url, suivant)`, `playUntil(s)`, `replay(s)`, `playFull()`, `stop()`, `unlock()`, signaux `state` (`idle`, `loading`, `ready`, `playing`, `finished`, `error`) et `position`. **Un échec est `error`, jamais `idle`** (piège 33) ; un échec de la lecture complète (après la révélation) est `finished`. **`HtmlAudioPort`** (décision du 13/10/2026 après la recette sur iPhone, #309 : Howler en Web Audio est écarté, cf. `docs/architecture/decisions.md`) : un seul élément `Audio` (`playsinline`) pour tous les extraits, lus en flux depuis le CDN de Deezer, aucune bibliothèque. `load` pose la source (`ready` à `canplay`, une seule fois). **Arrêt au palier calé sur le son réel** (piège 44) : chrono lancé à l'événement `playing` pour `palier − currentTime`, suspendu sur `waiting`, et boucle `requestAnimationFrame` qui coupe dès que `currentTime` atteint le palier (10 ms près) et alimente `position`. **Jamais de coupure à l'aveugle** (piège 46) : à l'échéance, le chrono relit `currentTime` et se reprogramme (20 ms au moins), rien ne coupe pendant un `seeking`. Deux jetons (`loadToken`, `playToken`) invalident les rappels d'un chargement ou d'une lecture périmés ; un `AbortError` de `play()` (notre propre `pause()` ou un changement de source) n'est pas une erreur. **« Écouter plus » pendant la lecture repousse l'arrêt sans couper le son**, arrêté à un palier il relit depuis le début jusqu'au nouveau palier, pendant le chargement il est gardé (piège 40). Un extrait plus court que le palier : sa fin est la fin du palier. Le suivant est seulement annoncé au navigateur (`<link rel="preload" as="audio">`, un seul à la fois, une fois le courant prêt) : rien n'est décodé en mémoire. **`unlock()`** (via `TrackRoundStore.unlockAudio()`) se fait dans le gestionnaire du clic, avant tout appel réseau : sur iPhone, un élément audio ne joue hors d'un geste qu'après avoir joué une fois dans un geste ; il fait jouer l'élément partagé jusqu'à ce qu'un essai passe, un refus se retentant au clic suivant (« Piste suivante », « Réessayer »), même avec un extrait chargé (#313) : sans extrait, ou avec un extrait en échec que « Réessayer » rechargera, un silence de 10 ms (adresse `blob:`, la CSP refusant `data:` pour les sons) ; avec un extrait chargé ou en chargement, l'élément le joue en muet puis revient à sa position, sans couper l'extrait ni la lecture demandée pendant le chargement (`start()` remet le son) ; pendant une lecture, il est déjà déverrouillé. À vérifier sur iPhone (#309). L'élément audio joue malgré le mode silencieux de l'iPhone. Une signature d'extrait expirée en cours de lecture donne `error` : la manche en redemande une fraîche d'elle-même une fois, puis « Réessayer » (piège 14). Aucun audio ni pochette Deezer n'est gardé hors du cache HTTP ordinaire du navigateur (piège 47).
- **Tests du lecteur** : `html-audio.port.spec.ts` joue de vrais sons dans Chromium (lancé avec `--autoplay-policy=no-user-gesture-required`, `vitest.config.ts`), mesure le temps jusqu'à la fin du palier et simule les démarrages lents de l'iPhone (son 400 ms après `play()`, faux `playing`). Les stores et composants utilisent `FakeAudioPort`.
- **Indices** : le nombre de boutons suit `HintPolicy` ; le front n'invente aucun niveau. Tous les niveaux débloqués et pas encore révélés se proposent ensemble. Libellé du bouton : `hintButtonKey(HintPolicy.kinds[niveau - 1])` (« Indice année », « Indice artiste », sinon « Indice N »). Étiquette d'un indice révélé : `hintLabelKey(kind)` (`year`, `artist…`, sinon générique) ; les types exacts viennent du back.
- **Entrée dans le champ** : `AnswerInputComponent` émet `enter` (l'événement clavier) et c'est la manche (`TrackRoundComponent.onEnter`) qui choisit la proposition en surbrillance, en lisant le store à cet instant et en empêchant alors la validation du formulaire. L'entrée `highlighted` du composant n'est mise à jour qu'au prochain cycle d'affichage : `↓` puis `Entrée` enchaînés vite (un E2E, un joueur rapide) la voyaient encore à -1 et validaient la saisie (trouvé par `autocomplete-keyboard-nav.spec.ts`).
- Les sélecteurs des E2E (champ « Artiste — Titre », ✕, « Valider », « Valider quand même », « ▶ Xs », « ↺ Xs », `data-testid="guess-time-chart"` et `data-bucket`) sont stables : ne pas les changer sans adapter les E2E.

`src/app/admin/`, quatre couches. La coquille et cinq onglets : **tableau de bord**, **défis**, **pool** (`/admin/catalogue`), **joueurs**, **actions** (le domaine `admin` peut importer `account`, pour `BrowserIdComponent`, et `gameplay`, pour l'histogramme des temps).
- `domain/` (TypeScript pur) : `PoolTrack` (disponible ou utilisé se déduit de `usageCount`), filtres (texte cherché dans l'artiste, le titre **et « artiste titre » collés**, piège 28 ; statut, extrait, plage de dernière utilisation), tri (**par défaut les disponibles avant les utilisés** ; désactivés toujours en fin ; valeurs vides en dernier), pagination par 15 ; le cooldown (`domain/actions.ts` : bornes de la part du pool, 10 à 90 %, **seuil d'alerte de 14 jours** et `cooldownTone` : rouge sous 7 jours, orange sous 14, vert au-delà, #275) ;
- `data-access/` : `CatalogueApi` (adaptateur du client, rend des types du domaine ; `findPreviewUrl` redemande l'extrait à Deezer, le pool n'en garde pas l'adresse signée), `PoolStore` (liste, filtres, tri, page, sélection, ajout, renommage, désactivation, suppression : **aucune mutation locale**, la liste est relue après chaque action ; les actions rendent l'erreur à afficher dans leur fenêtre ou `null`), `DeezerSearchStore` (panneau : attente de 300 ms, recherche annulée par la suivante, ajout par ligne, liaison avec le filtre, **active par défaut**), `AudioPreviewPlayer` (un seul son à la fois, aucun audio gardé, piège 47) ; `catalogue.providers.ts` donne l'adresse de l'API au client ;
- `feature/` : `AdminShellPage` (titre et ID navigateur centrés, barre des 5 onglets `ADMIN_TABS` de `admin-tabs.ts`, déconnexion sous le contenu ; accès : visiteur ou invité → « Connecte-toi d'abord » ; compte sans le rôle → « Accès refusé » ; admin → onglets et déconnexion ; l'ID navigateur est affiché dans tous les cas), `CataloguePage` (fournit `PoolStore`, `DeezerSearchStore` et `AudioPreviewPlayer`, câble la liaison filtre ↔ recherche, reprend et écrit `?page=` — numérotée à partir de 1, `replaceUrl` —, ouvre les fenêtres), fenêtres `PreviewTrackDialog` (écoute d'un morceau du pool, dont l'extrait est redemandé à Deezer, ou d'un résultat du panneau de recherche, lu avec l'extrait déjà reçu : le ▶ d'un résultat ouvre cette fenêtre au lieu de jouer dans le panneau), `EditTrackDialog` (renommer est permis **à tout moment, défi du jour compris**, avec un avertissement dans ce cas), `DeleteTrackDialog`, `ADMIN_ROUTES`, `provideAdmin()` (branché dans `app.config.ts`) ;
- `ui/` : `PoolToolbar`, `PoolFilterBar`, `PoolTable` (pagination comprise), `SearchPanel` (par résultat : ▶ qui ouvre la fenêtre d'écoute et un bouton « + », puis « … », « ✓ » ou « ! », nommé « Ajouter », « Ajouté » ou « Erreur » pour les lecteurs d'écran et les E2E), purement présentationnels.

**Onglets autres que le pool** (un module par onglet, chargé à la demande, ses stores fournis par la page ; chaque onglet ne charge ses données **qu'à son ouverture**, un E2E le vérifie) :
- **Tableau de bord** (`/admin/dashboard`, onglet d'arrivée) : `DashboardApi` (`GET /api/admin/daily/dashboard?date=`), `DashboardStore`, `DashboardPage` et ses briques (`dashboard-day-nav`, `dashboard-kpis`, `dashboard-activity`, `dashboard-players`). Les jours sont des jours UTC de jeu, mis en forme par `Intl` en UTC ; la langue arrive par une entrée.
- **Défis** (`/admin/defis`) : `ChallengesApi` (stats par défi, historique, `POST …/challenges/{date}/stats/recompute`), `ChallengesStore`, `ChallengesPage`, cartes de défi dépliables, navigateur de mois, **chips joueur** (le joueur du navigateur courant, `SessionStore.player().id`, porte « toi » ; clic gauche : surbrillance croisée, clic droit : copie de l'identifiant complet), pop-up histogramme (`TrackChartDialog`, `GuessTimeChartComponent` de `gameplay` en `showCounts`) et bouton « Recalculer les stats » sur les défis dont la photo est figée et recalculable (`canRecompute`, la date du calcul s'affiche).
- **Joueurs** (`/admin/joueurs`) : `AdminPlayersApi`, `AdminPlayersStore` (une seule ligne dépliée à la fois, l'historique relu à chaque dépliage), `PlayersPage`, lignes et historique de 30 jours. **L'email est masqué** (`c•••@gmail.com`, `maskEmail` de `admin/domain/registered-player.ts`) jusqu'au clic sur l'adresse (minimisation RGPD) ; le filtre cherche quand même dans l'adresse complète.
- **Actions** (`/admin/actions`) : `ActionsApi`, `ActionsStore`, `ActionsPage`. **Témoins des tâches planifiées** (lecture seule, `JobWitnessComponent`) : `JobsApi.getLastRuns` (`GET /api/admin/jobs/last-runs`, client `AdminClient`) donne le dernier passage de chaque tâche, que le domaine (`domain/actions.ts` : `challengeWitness`, `previewsWitness`) traduit en ton (`ok`, `warn`, `error`, `running`, `none`) et en message : « Défi généré le JJ/MM/AA à HH:MM », « déjà présent », avertissement `admin.pool_insufficient`, « N vérifiés, N corrigés » (avertissement si `failed > 0`), en cours, échec, prochain essai, prochain passage ; « Aucun passage ces 7 derniers jours » (rétention Hangfire). **Aucun bouton de lancement** : on lance une tâche depuis `/jobs` (« Déclencher maintenant »). Dernier passage et cooldown sont chargés ensemble à l'ouverture de l'onglet (`ActionsStore.load`). **Cooldown** (#275, `ActionCooldownComponent`) : la part du pool en cooldown lue à l'ouverture (`GET /api/admin/daily/settings`, `ActionsApi.getCooldown`), enregistrée par `PUT …/settings/track-cooldown-pool-percent` (10 à 90 %) ; en dessous, « Appliqué aujourd'hui : N jours · P morceaux jouables » (la réponse de l'API, recalée après chaque enregistrement) et, sous 14 jours, « Sous le seuil de 14 jours : ajoute des morceaux. » (rien n'est bloqué). La barre du pool montre aussi « cooldown N j » coloré (`PoolStore.cooldownDays`, relu à chaque lecture de la liste : il suit la taille du pool ; absent si sa lecture échoue, sans bloquer le pool). **Lien « Tâches planifiées »** vers `/jobs` (jeton `JOBS_DASHBOARD_URL`), dans l'onglet : visible d'un admin seulement, l'API refuse `/jobs` à tout autre (401/403). **Stories Instagram hebdomadaires** (`WeeklyStoryComponent`, `WeeklyStoryStore`, `StoryRenderer` : `html2canvas-pro`, chargé à la demande, fond `public/stories/fond-4.webp`) : sans pochette (piège 47).
- **Coquille** : les effectifs « Pool (55) », « Défis (30) », « Joueurs (12) » viennent de `AdminCounts` (service de la racine : les pages sont détruites au changement d'onglet), renseignés quand l'onglet a chargé ses données (avant, le libellé reste nu) et oubliés dès que le joueur de la session change (déconnexion, autre compte). **Heure de déploiement** (piège 25) : `core/shell/deployed-at.ts` lit `BUILD_TIME`, posé par `ng build --define` depuis l'argument de build Docker `BUILD_TIME` (`deploy.sh` l'exporte à chaque déploiement : un argument qui change invalide le cache de l'étape de build, sans lui l'heure resterait figée) ; sans définition (`ng serve`, tests, build local), rien ne s'affiche, et la coquille ne la montre qu'à un admin connecté. Pas de fichier généré : un `build-info.ts` ignoré par git casserait les tests unitaires hors build.
- **Textes** : par sections (`admin.dashboard.*`, `admin.actions.*`, `admin.players.*`…) ; les clés qui ne servent plus sont à nettoyer.

Règles : les fenêtres du pool s'ouvrent avec **`injector: inject(Injector)`** (option de `ModalService`) : sans elle, le CDK Dialog ne voit que la racine et ne trouverait pas `PoolStore`. Fermer la fenêtre d'écoute arrête le son et une réponse de Deezer arrivée après la fermeture ne relance rien (piège 42, testé). Un morceau utilisé ne se supprime pas (le bouton « Désactiver » le remplace) ; un morceau du défi du jour ne se désactive pas (bouton grisé). Les accès à l'admin sont revérifiés par l'API à chaque requête : l'écran d'accès n'est qu'un confort. La coquille met le `<router-outlet>` dans un bloc `w-full` : posé seul dans la colonne flex, il compterait comme un élément et doublerait l'écart avant l'onglet. Une page de l'admin prend toute la largeur (`host: { class: 'flex w-full min-w-0 justify-center' }`) : centrée par la coquille (`items-center`), elle prendrait sinon la largeur du tableau et déborderait de l'écran d'un téléphone au lieu de faire défiler le tableau seul.

## Conventions

Cf. CLAUDE.md racine § Architecture front : couleurs par `var(--…)`, un composant = `.ts` (+ `.html` s'il est long), `OnPush`, écouteurs globaux dans `host: {}`, état exposé en lecture seule, traductions dans chaque composant qui affiche du texte. En plus : **champs de saisie à 16 px au moins sur écran tactile** (règle `@media (pointer: coarse)` de `styles.scss`, hors couche donc devant `text-sm` : sous 16 px, Safari sur iPhone zoome au toucher et garde le zoom) ; modales **uniquement** par `ModalService` (plus de modale maison ; `injector` pour qu'une fenêtre retrouve les stores de sa page), boutons par `appButton`.
