# CLAUDE.md — back v2 (refonte)

Back de la v2 d'InSeconds, en construction à côté de la v1 (`src/back/`), qui reste en service jusqu'à la bascule. Plan de référence : [`docs/refonte-v2/PLAN.md`](../../../docs/refonte-v2/PLAN.md) et [`docs/refonte-v2/DEVELOPPEMENT.md`](../../../docs/refonte-v2/DEVELOPPEMENT.md). Ce fichier décrit ce qui existe **déjà** dans le code ; il grossit à chaque PR.

État : **PR E3, back des statistiques** (après E1 le défi du jour et E2 les parties) (après la phase A, puis B1 : identité et cookie, B2 : connexion par lien magique, B3 : profil et appareils, B4 : import des joueurs v1, B5 : identité du joueur dans la télémétrie et document OpenAPI des joueurs, puis C1 : back du Catalogue, C2 : import du Catalogue, C3 : front du pool admin). Module `Players` : invités, appareils, cookie standard validé en base, reprise des cookies v1, clés Data Protection chiffrées par certificat, connexion par lien magique et dev-login, pseudo, changement d'email, déconnexion, liste et révocation des appareils, purge des jetons expirés (cf. « Authentification » et « Module Players »). Module `Catalogue` : morceaux du pool (renommer, désactiver, contrôler l'extrait, rang), client Deezer découpé en ports avec cache (`InSeconds.Deezer`), recherche publique, routes admin du pool, tâche `catalogue-refresh` et bouton « Re-vérifier les previews » par Hangfire, faux Deezer dans l'hôte de test, document OpenAPI `catalogue` (cf. « Client Deezer » et « Module Catalogue »). `Daily` : les défis, leur génération (nocturne, à la volée, bouton de l'admin), l'usage des morceaux calculé sur les défis (E1), puis les parties, le score, la série et les gels (E2), et les statistiques (E3, cf. « Module Daily »). `Gameplay` : la mécanique d'un morceau (D1). Import v1 → v2 des parties Players (B4) et Catalogue (C2) : `deploy/migration-v2/` (cf. « Import v1 → v2 »). Le front du compte (B5) dépend de Players ; celui du pool admin (C3) dépend de Catalogue.

## Commandes

```bash
cd src/v2/back
dotnet build InSeconds.slnx
dotnet test --solution InSeconds.slnx      # unitaires + architecture + intégration (Docker requis)
dotnet run --project InSeconds.Api          # http://localhost:5175
dotnet run --project InSeconds.Api -- --migrate-only   # applique les migrations puis rend la main
dotnet run --project InSeconds.Api -- --rotate-data-protection-key   # crée une clé Data Protection neuve (après un import, B4)
dotnet run --project InSeconds.Api -- --freeze-day-stats   # fige les stats des jours terminés sans photo (après un import, E4)
dotnet run --project InSeconds.Api.Testing  # hôte de test (Development) : API + /api/e2e + faux email + faux Deezer

# Image de prod (contexte src/v2/back), sans l'hôte de test
docker build -f InSeconds.Api/Dockerfile -t inseconds-api-v2 .

# Régénérer le code Wolverine (après tout ajout ou changement de handler / endpoint), puis commiter
rm -rf InSeconds.Api/Internal/Generated && dotnet run --project InSeconds.Api -- codegen write

# Nouvelle migration (depuis src/v2/back/InSeconds.Api)
dotnet ef migrations add <Nom> --output-dir Infrastructure/Persistence/Migrations
```

`global.json` fixe le lanceur de tests **Microsoft.Testing.Platform** (`test.runner`) : avec le SDK .NET 10, `dotnet test` refuse l'ancien mode VSTest pour xUnit v3. D'où `dotnet test --solution …` (et non `dotnet test InSeconds.slnx`).

## Règles

- **Rien dans le schéma `public`** : la v2 partage la base de la v1 jusqu'à la bascule, et toutes les tables v1 sont dans `public`. Chaque entité déclare son schéma (`infra`, puis un schéma par module). L'historique EF est `infra.__ef_migrations_history`. Vérifié par `PersistenceTests` et `DatabaseTests`.
- **Noms en snake_case** (`EFCore.NamingConventions`).
- **`citext` vit dans le schéma `extensions`** (pas dans `public`). Ses opérateurs, dont `=`, n'y sont trouvés que si `extensions` est dans le `search_path` : `DatabaseServiceCollectionExtensions.WithExtensionsSearchPath` l'ajoute à la chaîne de connexion. Sans lui, PostgreSQL compare en `text`, sensible à la casse, sans aucune erreur (constaté en A1). Toute connexion ouverte hors du `DbContext` sur une colonne `citext` doit passer par cette méthode.
- **Jamais `DateTime.UtcNow`/`Now`/`Today`** (ni `DateTimeOffset`) dans `InSeconds.Api` : l'heure vient de `TimeProvider` ou d'`IGameCalendar` (`Now`, `Today`, `StartOf(jour)`), remplaçables en test par `FakeTimeProvider`. Vérifié par `ClockUsageTests` (scan des sources).
- **Erreurs** : toute réponse d'erreur est un ProblemDetails avec `code` (`ErrorCodes`, ex. `common.not_found`) et `traceId` (32 hex, recherchable dans Grafana). Sur un 500, titre générique, ni `detail` ni exception. Les modules ajouteront leurs propres codes (`daily.xxx`…).
- **Tests** : `Assert` de xUnit uniquement (pas de FluentAssertions, licence payante depuis la v8). Une base neuve par classe de tests d'intégration (`PostgresFixture.CreateDatabaseAsync`), un seul conteneur pour toute la suite.

## Réglages (`infra.settings`)

Une ligne par réglage : `key` = chemin de configuration complet (`Daily:GuessTimerSeconds`), `value` en `jsonb`. `DatabaseSettingsConfigurationProvider` lit la table et l'aplatit dans `IConfiguration` (`SettingsJsonFlattener` : objet → `clé:propriété`, tableau → `clé:0`, `clé:1`…). Les modules lisent leurs options par `IOptionsMonitor<T>` : **tout est relu à chaud**, sans redémarrage.

- Écrire un réglage : `SettingsStore.SetAsync(key, value)` (upsert puis rechargement).
- Après une écriture SQL directe : `ISettingsReloader.Reload()`.
- Le provider ignore seulement « base, schéma ou table absents » (premier démarrage avant migration) ; toute autre erreur SQL empêche le démarrage.
- **Pas de clé de dictionnaire décimale** : le binder .NET laisse un `Dictionary<decimal, …>` vide sans erreur. D'où `DurationScores` stocké en liste d'objets `[{"seconds":0.5,"score":1000},…]`. Les clés `string`, entières ou `enum` fonctionnent (`HintPenaltyPercent` : `{"1":30,"2":60}` → `Dictionary<int,int>`).

## Démarrage

`Program.cs` appelle `ApiComposition.AddInSecondsApi(args)` puis `UseInSecondsApi()`, partagés avec l'hôte de test. Services : réglages en base → OpenTelemetry → `DbContext` → migrations → calendrier → ProblemDetails → health checks → Data Protection → auth → proxies de confiance → rate limiting → email → client Deezer → Wolverine → Hangfire → `App:PublicUrl` → modules (`AddPlayers`, `AddCatalogue`, `AddDaily`). Pipeline : `UseForwardedHeaders` (en premier : tout le reste voit l'IP réelle) → en-têtes de sécurité → erreurs → CORS → authentification → transition des cookies v1 → autorisation → rate limiter → routes. Puis `RunJasperFxCommands(args)` (démarre l'API, ou exécute une commande Wolverine comme `codegen write`). Les migrations passent par `DatabaseStartupService` (`IHostedLifecycleService.StartingAsync`) : avant le démarrage de Wolverine et Hangfire, sauf si `Database:MigrateOnStartup=false` ; les réglages sont rechargés juste après (la table peut ne pas avoir existé à la construction de la configuration). Une commande Wolverine ne démarre pas l'hôte : pas de migration, et pas de lecture des réglages en base (`CommandLine.StartsServer`), pour que la CI génère le code sans base.

`--migrate-only` (`MigrateOnlyCommand`) : hôte minimal (base seulement, ni serveur web ni tâche de fond), applique les migrations et rend la main avec le code 0. Sert au déploiement et à l'import des données v1.

`--freeze-day-stats` (`FreezeDayStatsCommand`, E4) : hôte minimal (base, réglages lus en base, calendrier, règles du jeu et fournisseurs d'indices ; ni serveur, ni Wolverine, ni Hangfire), refuse de figer quoi que ce soit (code 1) si les réglages ne passent pas le contrôle du démarrage de l'API (`DailyOptionsChecks.Problems`), fige les statistiques de **tous les jours terminés (J-2 et avant) sans photo**, du plus ancien au plus récent, par `CloseChallengeDayHandler.Handle` (la règle de la tâche `daily-close-day`), **une transaction par jour** (le verrou du jour en demande une). Un jour qui échoue n'empêche pas les suivants : code de sortie 1 à la fin. Rejouable. À lancer après l'import complet (les paliers et le barème figés sont ceux des réglages).

`--rotate-data-protection-key` (`RotateDataProtectionKeyCommand`, B4) : même principe (base et Data Protection seulement, le host n'est jamais démarré), crée par `IKeyManager.CreateNewKey` une clé active tout de suite, valable 90 jours, chiffrée par le certificat (exigé en prod et en staging). À lancer après chaque import v1 → v2, cf. « Import v1 → v2 ».

## Wolverine (`Infrastructure/Messaging/WolverineSetup.cs`)

- Endpoints en **Wolverine.Http** (`[WolverineGet]`…), validation FluentValidation en ProblemDetails. Toute route `/api/admin*` reçoit la policy Admin (`ConfigureEndpoints`) : impossible d'oublier l'attribut.
- **Service location** interdite par défaut (le code généré construit lui-même les dépendances, d'où des implémentations publiques) ; seules exceptions (`AlwaysUseServiceLocationFor`) : `IEmailSender`, choisi au démarrage par une fabrique (Brevo, redirigé, capturé), et les ports Deezer (`IPreviewProvider`, `ITrackSearch`, `ITrackMetadataSource`, `CachedTrackSearch` : client HTTP typé et décorateurs enregistrés par fabrique, cf. « Client Deezer »).
- `AutoApplyTransactions` + transactions EF Core : un handler qui modifie le `DbContext` et publie un message fait **une seule transaction** (donnée + outbox). Messages durables dans le schéma **`messaging`** (`PersistMessagesWithPostgresql(cs, "messaging")`, files locales durables). Vérifié par `Messaging/OutboxTests` : message envoyé seulement si la donnée est enregistrée, et aucun message ni enveloppe sinon.
- **Les tables de `messaging` sont créées par Wolverine au démarrage, pas par les migrations EF.** `MapWolverineEnvelopeStorage("messaging")` ne fait que les déclarer au `DbContext` (exclues des migrations ; la migration `MapWolverineEnvelopeStorage` est vide exprès). `--migrate-only` ne les crée donc pas.
- **Codegen statique** : en Production et Staging, `TypeLoadMode.Static` (`WolverineSetup.UsesStaticCodegen`) ; le code est lu dans `Internal/Generated`, commité. Ailleurs, génération à la volée (`UseRuntimeCompilation`). Oublier de régénérer = l'API refuse de démarrer en staging (`MissingPreBuiltTypesException`, testé par `StaticCodegenTests`) ; le job CI `back-v2` supprime le dossier, relance `codegen write` et échoue si le résultat diffère du dépôt. `codegen write` ne supprime pas les fichiers périmés : toujours `rm -rf` avant.

## Tâches planifiées (Hangfire, `Infrastructure/Jobs/`)

- Stockage PostgreSQL dans le schéma **`jobs`** (créé par Hangfire au démarrage, comme `messaging`). Serveur de tâches si `Jobs:Server:Enabled` (défaut `true`, `false` dans les tests d'intégration), `Jobs:Server:WorkerCount` (défaut 2 : peu de tâches, et chaque worker tient une connexion).
- **Déclarer une tâche** : une classe `IScheduledJob` (`RunAsync` renvoie un résultat sérialisé en JSON, ou `null`), enregistrée par `services.AddScheduledJob<TJob>("id", Cron.Daily())`. Planning surchargeable par `Jobs:<id>:Cron`, fuseau UTC. `RecurringJobsRegistrar` enregistre les tâches au démarrage et **supprime celles qui ne sont plus déclarées**. Ajouter la tâche à `ExpectedJobs` de `Jobs/ScheduledJobsTests` (aujourd'hui : `catalogue-refresh`, C1, `players-purge-expired-tokens`, B3, `daily-generate-challenge` et `daily-generate-challenge-admin`, E1).
- **Lancer une tâche à la demande** (un bouton de l'admin) : `IJobTrigger.TriggerAsync(idDeTâche)` renvoie l'identifiant de l'exécution (202 + `JobExecutionResponse`), ou celui de l'exécution déjà en file ou en cours (un second clic la suit). Le front suit par `GET /api/admin/jobs/{id}`. Usages : `POST /api/admin/catalogue/refresh-previews` (C1) et `POST /api/admin/daily/challenges/generate-today` (E1).
- **Compte rendu** : une tâche qui rend un objet voit ses propriétés à zéro absentes du JSON (Hangfire), et un `$type` : rendre un dictionnaire (`PreviewRefreshResult.ToReport()`) pour avoir toutes les clés.
- **Échec métier** : lever `JobFailedException("module.code")` ; le code est renvoyé tel quel. Toute autre exception est rendue en `common.unexpected` (ni message ni pile exposés).
- **Tableau de bord `/jobs`** : policy Admin (401 anonyme, 403 joueur), `Authorization = []` (le filtre par défaut de Hangfire n'accepte que localhost), jeton antiforgery exigé sur ses actions. À protéger en plus par Cloudflare Access avant la mise en ligne (S3).
- **`GET /api/admin/jobs/{id}`** : état d'une exécution (`queued`, `processing`, `succeeded`, `failed`, `retry_scheduled`, `deleted`), `result` (JSON) si réussie, `errorCode` si échouée ; 404 `common.not_found` si l'id est inconnu.
- **Tests avec un vrai serveur Hangfire** (`Jobs:Server:Enabled=true`, ex. `JobStatusTests`) : dans la collection `HangfireServerCollection`, qui passe seule. Hangfire garde son activateur de tâches en global : une autre API de test créée puis détruite en parallèle le remplace, et la tâche échoue sur un `IServiceProvider` détruit (vu en CI sur la PR A6).

## Services transverses (`InSeconds.Infrastructure`)

Projet sans dépendance vers l'API ni les modules (vérifié par `ArchitectureTests/ProjectDependencyTests`). L'API l'utilise par ses méthodes d'extension.

- **Emails** (`Email/`) : les modules dépendent de `IEmailSender` seulement. `BrevoEmailSender` (API transactionnelle Brevo, `Brevo:ApiKey`/`SenderEmail`/`SenderName`, vérifiés au démarrage en Production et Staging). Si `EmailRedirect:To` est renseigné, `RedirectingEmailSender` envoie tout à cette adresse avec un bandeau (objet inchangé) ; **obligatoire en Staging** (l'API refuse de démarrer sans, `EmailStartupTests`). Journaux : sujet et identifiant Brevo (EventId 1007/1101 comme en v1), **jamais l'adresse**, ni celle que le message d'erreur Brevo pourrait citer.
- **OpenTelemetry** (`Observability/`) : mêmes réglages que la v1 (`inseconds-api`, ASP.NET Core, HttpClient, Npgsql, Wolverine, runtime ; logs avec scopes). Export OTLP seulement si `OTEL_EXPORTER_OTLP_ENDPOINT` est défini. `/health` et `/jobs` exclus des traces. Une activité par exécution Hangfire (source `InSeconds.Jobs`, `Jobs/JobTracingFilter` dans l'API). **Confidentialité** : jamais d'email, de pseudo, de réponse saisie, de cookie ni d'`Authorization` ; aucune capture d'en-têtes.
- **Proxies de confiance** (`Networking/TrustedProxyNetworks`) : RFC1918 + loopback (Caddy) et plages Cloudflare, `ForwardLimit = null` (piège 27 du CLAUDE.md racine). Un en-tête `X-Forwarded-For` forgé par un appelant hors de ces plages est ignoré.
- **Rate limiting** (`RateLimiting/`) : fenêtres glissantes, par IP réelle ou par joueur (`PartitionBy`), noms et limites de la v1 (`RateLimitPolicies` : `magic-link-request` 5/10 min par IP, `email-change-request` 5/10 min **par joueur**, `device-revocation` 20/10 min **par joueur** (B3, S11), `player-creation` 30/10 min, `client-error-report` 20/5 min, `deezer-search-public` 60/5 min, par IP, posée sur `GET /api/catalogue/search` depuis C1). L'identifiant du joueur est fourni par l'API (`AddInSecondsRateLimiting(configuration, playerKey)`, claim `player_id`) : l'infrastructure ne connaît pas ses claims ; sans joueur identifié, une limite par joueur retombe sur l'IP. Une route s'y inscrit par `RequireRateLimiting(RateLimitPolicies.X)`. Refus : 429 ProblemDetails (`common.too_many_requests`, `Retry-After`). `RateLimiting:Enabled=false` en test (`ApiFactory`, `appsettings.Testing.json` de l'hôte de test) : les politiques restent sur les routes mais ne limitent rien.
- **CORS** (`Http/CorsSetup`) : politique par défaut, repris de la v1 (`AllowAnyHeader`, `AllowAnyMethod`, `AllowCredentials`), origines dans `Cors:AllowedOrigins`. **Aucune par défaut** : en développement et en E2E, le front passe par le proxy d'`ng serve` (même origine). Staging : `https://dev.inseconds.cc` (`appsettings.Staging.json`) ; prod : `https://inseconds.cc` et `https://www.inseconds.cc` (`appsettings.Production.json`, sans effet avant la bascule). `UseCors` juste après la gestion des erreurs (les en-têtes, posés au démarrage de la réponse, restent sur un 500 : le front lit son code d'erreur) et avant l'authentification et le rate limiting (une requête préalable `OPTIONS` passe sans cookie ni quota). Tests : `Security/CorsTests`.
- **En-têtes de sécurité** (`Http/SecurityHeaders`, S15) : `nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, HSTS 1 an, CSP `default-src 'none'; frame-ancestors 'none'` sur l'API. Le tableau de bord `/jobs` a sa propre CSP : scripts de `/jobs` seulement (Hangfire n'a aucun script en ligne, vérifié par `SecurityHeadersTests`), styles en ligne permis (attributs `style`). Posés au démarrage de la réponse, donc aussi sur les erreurs.

## Hôte de test (`InSeconds.Api.Testing`)

`TestingProgram` : la même composition que l'API, plus les faux et les routes `/api/e2e`. Refuse de démarrer hors `Testing` et `Development`. Jamais dans l'image de prod (S9) : l'API ne le référence pas (`ProjectDependencyTests`), le `Dockerfile` ne le copie pas, et le job CI `back-v2` construit l'image et échoue si `InSeconds.Api.Testing` s'y trouve.

- `CapturingEmailSender` remplace `IEmailSender` (les emails restent en mémoire).
- **Faux Deezer** (`Deezer/FakeDeezerHandler`, C1) : `AddFakeDeezer()` remplace le **transport HTTP** du vrai client Deezer (`ReplaceDeezerHttpHandler`) : le vrai client et le vrai cache tournent sur ce faux. Conventions de la v1 : un morceau d'identifiant ≥ `NoPreviewFrom` (9 000 000 000) n'a pas d'extrait ; ≥ `NotFoundFrom` (8 000 000 000) : inconnu de Deezer (erreur 800 en HTTP 200) ; ≥ `QuotaFrom` (7 000 000 000) : quota dépassé (erreur 4 en HTTP 200, piège 16) ; la recherche répond un morceau, ou, pour une requête contenant `dedup-test`, trois variantes parenthésées du même morceau et un morceau distinct. L'extrait est `http://localhost:{E2E_FRONT_PORT ou 5176}/test-audio.mp3` (**le front v2 n'a pas encore ce fichier : il arrive avec les E2E du pool, C3**). `FakeDeezerState` (singleton) garde les requêtes reçues et un `Intercept` que le test peut poser (quota, panne, réponse lente). Pas de résilience HTTP (`Deezer:ResilienceEnabled=false` dans les `appsettings` de l'hôte). `ApiFactory` des tests d'intégration le branche toujours (jamais le vrai Deezer) et expose `FakeDeezer`.
- `POST /api/e2e/reset` : vide (Respawn) les tables de **tous les schémas sauf** `public` (tables v1), `infra`, `extensions`, `messaging` et `jobs`, lus en base à chaque appel (un nouveau module est couvert sans rien changer : `players` depuis B1, `catalogue` depuis C1), les emails capturés, et remet le faux Deezer (requêtes, `Intercept`) et son cache à zéro.
- `POST /api/e2e/seed-catalogue` (C1, réaliste en C3) : le pool de test de la v1, **55 morceaux réels dans l'ordre exact de la v1** (`E2E/CatalogueSeed`, les index comptent : 0-4 défi d'avant-hier, 5-9 d'hier, 10-14 du jour, 15-20 cooldowns variés, le reste le pool), 50 jouables et 5 sans extrait (identifiants Deezer ≥ 9 000 000 000), `{ added }` ; rien si le pool n'est pas vide. Année `1990 + index % 30`, rang `500 000 + index`.
- **Usage des morceaux** (E1) : plus de simulation (`E2eTrackUsage`, C3, est retirée) : le seed écrit de **vrais défis** (`daily.challenges` et `daily.challenge_tracks`) que le vrai `ITrackUsage` de Daily relit, avec le même usage que la v1 (0-4 : défi d'avant-hier, 5-9 : d'hier, 10-14 : du jour, `inTodayChallenge`, `usageCount` 1 ; 15 jamais utilisé ; 16 : -5 j ; 17 : -30 j, 3 usages ; 18 : -31 j, 2 ; 19 : -90 j, 7 ; 20 : -15 j ; les usages répétés sont à une semaine d'écart, un défi par jour où un morceau a servi). `unlockDate` = dernier usage + `Daily:TrackCooldownDays`. Vidé par `/reset` (les tables du schéma `daily` le sont comme les autres).
- `POST /api/e2e/reseed` (C3) : remise à zéro complète (comme `/reset`) puis seed du catalogue et de l'usage ; idempotent. L'`Authorization` du fixture E2E est ignorée.
- `POST /api/e2e/login-as-admin` (C3) : connecte le navigateur appelant (cookie posé dans la réponse) comme le compte lié `admin-e2e@e2e.test` / `AdminE2E`, créé au besoin, par le chemin du dev-login (`AccountSignIn`, nouvelle session d'appareil), puis `is_admin = true` en base. Le rôle est relu en base par le validateur et la session est neuve : aucun cache périmé. Au premier appel, l'invité du navigateur (s'il existe) devient le compte admin, comme au premier lien magique ; ensuite, on se connecte au compte existant. Un cookie d'un joueur effacé par un reset est toléré.
- `GET /api/e2e/last-email?to=` : dernier email envoyé à cette adresse (404 sinon).

## Client Deezer (`InSeconds.Deezer`, C1)

Projet à la racine de `src/v2/back` (§ 5.1 du plan), qui ne connaît ni l'API, ni `InSeconds.Infrastructure`, ni aucun module (vérifié par `ArchitectureTests/ProjectDependencyTests`). Le client Deezer de la v1, découpé en trois ports **par besoin** (§ 5.3) :

| Port | Rôle | Résultat |
|---|---|---|
| `IPreviewProvider` | l'extrait audio d'un morceau (URL signée de 30 s), pour le jeu | `PreviewLookup` : `Found(url)`, `Missing` (réponse déterminée : pas d'extrait, ou morceau supprimé), `Unavailable` (quota, panne : l'état est **inconnu**) |
| `ITrackMetadataSource` | artiste, titre, pochette (hash), année de sortie, **rang Deezer** (`rank`), extrait : l'état réel chez Deezer | `TrackMetadataLookup` : `Found(DeezerTrack)`, `NotFound`, `Unavailable` |
| `ITrackSearch` | recherche par texte | `SearchLookup` : `Found(tracks)` (liste vide si rien ne correspond), `Unavailable` (quota, panne : l'échec est journalisé) ; un résultat sans identifiant est écarté |

- **Jamais de `null` ambigu** : trois cas explicites, et seul le premier ou le deuxième permet de conclure (piège 16 du CLAUDE.md racine).
- **Erreurs en HTTP 200** (piège 16) : Deezer renvoie quota (code 4), service occupé (700), morceau supprimé (800) dans un payload `{"error":{…}}` qui contourne la résilience HTTP. Le code **800** (« no data ») est une réponse déterminée (`Missing` / `NotFound`) ; tout autre code, connu ou futur, et toute erreur HTTP ou de lecture donnent `Unavailable`.
- **Jamais de `catch {}` nu** (piège 13) : `OperationCanceledException` est relancée **seulement si l'annulation vient de l'appelant** (`ct`) ; le délai d'attente interne d'un `HttpClient` lève la même exception et est un échec de Deezer (`Unavailable`, journalisé en `Warning`) ; le reste est journalisé en `Warning` (`DeezerLog`, EventId 1210 à 1214). **Jamais le texte d'une recherche dans les journaux** (piège 36) : seulement sa longueur (`QueryLength`).
- **Un seul `DeezerClient`** (`HttpClient` typé) implémente les trois ports : un appel `/track/{id}` donne à la fois l'extrait, le rang, l'année et la pochette (le contrôle nocturne n'a besoin que d'une requête par morceau). `release_date` donne l'année (**null si elle est inférieure à 1** : Deezer met « 0000-00-00 » pour une date inconnue), `rank` le rang, un morceau dont l'artiste ou le titre est vide ou blanc est « introuvable » (422 à l'ajout, jamais une exception de domaine donc une 500), le hash de pochette est extrait de `album.cover_medium`. **`GetTrackAsync` renvoie l'identifiant demandé**, pas le champ `id` de la réponse (comme en v1) : c'est sur lui que le pool a vérifié les doublons, et une réponse sans `id` donnerait 0.
- **Cache** (`DeezerCache` : un `MemoryCache` **dédié**, 2000 entrées au plus, pas l'`IMemoryCache` partagé) : décorateurs des ports, pas le client.
  - `CachedPreviewProvider` : extrait en cache 24 h au plus, **borné par l'`exp` de la signature de l'URL** (`?hdnea=exp=…`) moins 1 h de marge (piège 14) ; pas de cache s'il reste moins d'1 h ou si la signature est expirée ; jamais le cache d'un `Missing` ni d'un `Unavailable`. **Priorité haute** (`CacheItemPriority.High`) : le cache est partagé avec les recherches publiques, qu'un script peut multiplier ; quand il est plein, ce sont elles qui partent d'abord.
  - `CachedTrackSearch` : recherche en cache 1 h (clé : limite + texte rogné en minuscules), jamais un `Unavailable` ni une liste vide.
  - **Une `Size = 1` sur chaque `cache.Set`** (piège 24) : sans elle, `MemoryCache` avec une `SizeLimit` lève une exception à l'exécution (testé avec le vrai `DeezerCache`).
- **Enregistrement** (`AddDeezer(configuration)`, appelé par `ApiComposition` avant Wolverine) : `IPreviewProvider` est le décorateur à cache (l'URL suffit au jeu, Gameplay/Daily plus tard) ; `ITrackSearch` et `ITrackMetadataSource` sont le client **brut** (admin, ajout, actualisation, contrôle des extraits veulent l'état réel) ; la recherche publique demande le décorateur concret `CachedTrackSearch`. Ce sont des fabriques : `WolverineSetup` les déclare à `AlwaysUseServiceLocationFor` (`DeezerServiceCollectionExtensions.ServiceLocationTypes`), sinon `codegen write` refuse (service location interdite).
- **Réglages** : `Deezer:BaseUrl` (défaut `https://api.deezer.com`), `Deezer:ResilienceEnabled` (défaut `true`, `false` dans l'hôte de test et dans `ApiFactory` : une condition par configuration, jamais sur l'environnement). Avec la résilience : timeout 4 s par tentative, 15 s au total, nouvelles tentatives exponentielles (429, 5xx), coupe-circuit sur 30 s.
- **Faux** : `ReplaceDeezerHttpHandler(createHandler)` remplace le transport HTTP (le vrai client et le vrai cache tournent sur le faux). Cf. « Hôte de test ».
- Usage : **piège 47** du CLAUDE.md racine (conditions de l'API Deezer) : jamais d'audio ni de pochette Deezer stockés (le pool ne garde que le hash de la pochette) ni dans un cache persistant. La recherche publique ne renvoie que artiste et titre.
- Tests : `UnitTests/Deezer/DeezerClientTests` (les trois ports, erreurs en 200, annulation, journaux sans la requête), `DeezerCacheTests` (TTL borné par la signature avec une horloge simulée, tailles, rien de mis en cache sur absence ou échec).

## Module Daily (`Modules/Daily/`, E1 et E2)

Le défi du jour (§ 3.1 et 4.4 du plan v2). Point d'entrée `DailyModule.AddDaily()` (appelé **après** `AddCatalogue`, car il remplace son `NoTrackUsage`). E1 : les défis, leur génération et l'usage des morceaux. E2 : les parties, le score, la série et les gels (cf. « Parties (E2) » plus bas) ; les stats arrivent en E3, l'import de l'historique en E4. Daily n'utilise de Catalogue que `Contracts`, et de Gameplay que `Contracts` (`ISeededShuffle`) ; Catalogue et Gameplay ne connaissent pas Daily (testé : `CatalogueEtGameplay_NeConnaissentPasDaily`, `Daily_NeDependQue…`).

- **Tables** (schéma `daily`, migration `Daily`) : `challenges` (`id` tiré d'une séquence HiLo `challenges_hilo`, `date` **unique** : `ix_challenges_date`, `seed`, `origin` : 1 nocturne, 2 à la volée, 3 admin, vide pour l'historique repris) et `challenge_tracks` (PK `(challenge_id, position)`, unique `(challenge_id, track_id)`, index sur `track_id` pour le cooldown, clé étrangère vers `catalogue.tracks` en `RESTRICT`). **La clé étrangère vers Catalogue est déclarée par le nom du type** (`HasOne("…Catalogue.Domain.Track", navigationName: null)`), pas par son type : Daily ne peut pas référencer le domaine de Catalogue. Aucune navigation entre modules, seulement des identifiants.
- **Domaine** (`Domain/`) : `DailyChallenge.Create(date, origine, morceaux)` (positions de 1 à N dans l'ordre du tirage, un morceau une seule fois, la graine est `DayNumber`, comme en v1), `ChallengeTrack`, `ChallengeOrigin`, `IDailyStore` (verrou de génération, lecture, ajout), `ITrackSelector` / `CooldownSeededSelector` (§ 5.3) → `TrackSelection(TrackIds, EligibleCount, Requested)`.
- **Tirage** (`CooldownSeededSelector`) : retire les morceaux en cooldown, **trie les candidats par identifiant** (le défi ne dépend ni de l'ordre rendu par la base, ni d'un doublon), puis Fisher-Yates à graine (`ISeededShuffle`, même algorithme que la v1) et garde les N premiers. Moins de N candidats : sélection vide, `IsSufficient` faux. Les candidats viennent de **`ITrackDirectory.ListPlayableIdsAsync`** (contrat de Catalogue, ajouté en E1) : non désactivés et extrait **disponible** (jamais « inconnu »), triés par identifiant.
- **Usage des morceaux** (`EfTrackUsage`, remplace `NoTrackUsage`) : **calculé** sur `challenge_tracks` + `challenges.date`, jamais stocké. `LastUsedDate` = dernier jour, `UsageCount` = nombre d'apparitions, `UnlockDate` = dernier jour + `Daily:TrackCooldownDays`, `InTodayChallenge` = apparu au jour de jeu en cours (`IGameCalendar`). **Cooldown de la v1, gardé tel quel** : un morceau tiré à une date ≥ jour − cooldown reste exclu (`LastUsedDate < jour − cooldown` pour être tirable). Il redevient donc tirable **le lendemain** de l'`UnlockDate` affichée au pool admin (écart d'un jour que la v1 avait déjà, voir DEVELOPPEMENT.md « Fait en E1 »). `GetTracksInCooldownAsync(jour)` sert aussi au contrôle nocturne des extraits (`catalogue-refresh`, qui demande demain).
- **Réglages** (`DailyOptions`, `IOptionsMonitor`, relus à chaud ; défauts de la v1, aucune ligne en base nécessaire) : `Daily:TracksPerChallenge` (5, ne change que les nouveaux défis : la fin de partie compte les morceaux réels, piège 38) et `Daily:TrackCooldownDays` (30).
- **Génération** (`GenerateDailyChallenge(Day, Origin)`, handler Wolverine, **une seule transaction**) : une seule logique pour la tâche de minuit, le secours à la volée (appelé par le démarrage d'une partie en E2) et le bouton. Étapes : **verrou consultatif** `pg_advisory_xact_lock(DAIL, numéro du jour)` (`IDailyStore.LockGenerationAsync`, refuse de tourner hors transaction) → défi déjà là : `AlreadyExists` sans rien changer → tirage → `Created`, ou `PoolInsufficient` sans rien écrire. **La course entre deux générations** (minuit et un joueur, ou deux clics) est donc réglée par le verrou : la seconde attend, voit le défi de la première et ne tire rien, sans passer par l'erreur de l'index unique ; testé avec un sélecteur lent (4 générations simultanées : une `Created`, trois `AlreadyExists`, un seul tirage) et deux jours différents qui ne s'attendent pas. Le résultat `GenerateChallengeResult` porte l'issue, le défi, le nombre de morceaux et ce qu'il manquait ; `ToReport()` en fait le compte rendu des tâches (`{ created, date, challengeId, tracks }`).
- **Tâches** (`IScheduledJob`, une ligne chacune, § 5.4 bis) :
  - `daily-generate-challenge` (`0 0 * * *`, UTC ; **tourne aussi en staging**, elle n'appelle pas Deezer) : génère le défi du jour de jeu en cours (`IGameCalendar.Today`), origine nocturne. **Un pool insuffisant lève `JobFailedException("admin.pool_insufficient")`** pour que Hangfire réessaie : `[AutomaticRetry(Attempts = 144, DelaysInSeconds = [600])]`, un essai toutes les 10 minutes pendant 24 h (le défaut de Hangfire s'arrête à 10 essais, 1 h 40 ; testé). `[DisableConcurrentExecution]`. Un défi déjà présent est un succès (`created: false`).
  - `daily-generate-challenge-admin` (**en pause**, `Cron.Never()`, **sans réessai**) : ce que lance le bouton, origine « admin ». Une tâche à part pour deux raisons : la tâche de minuit ne peut pas recevoir de paramètre, donc l'origine ne se déduirait pas ; et un clic de l'admin ne doit pas réessayer pendant 24 h, il voit tout de suite le résultat ou le code d'erreur. Elle apparaît dans l'historique de `/jobs` sous son nom. Les deux se protègent mutuellement par le verrou de génération, pas par `DisableConcurrentExecution`.
- **Route** : `POST /api/admin/daily/challenges/generate-today` (`generateToday`, policy Admin, 202 + `JobExecutionResponse`, `Location: /api/admin/jobs/{id}`) : déclenche `daily-generate-challenge-admin` par `IJobTrigger` ; un second clic pendant l'exécution suit la même. Compte rendu et code d'erreur lus par `GET /api/admin/jobs/{id}`. Code d'erreur publié : `admin.pool_insufficient` (`DailyErrorCodes`, nom du plan § 5.6, ne jamais le renommer).
- **Journal** (`DailyLog`, EventId 1300 à 1302) : défi généré (information), déjà présent (information), pool insuffisant (**erreur**, comme en v1 : c'est ce qui doit alerter, et il se répète à chaque essai).
- **Import** : `10-import.sql` vide désormais `daily.challenge_tracks` et `daily.challenges` avant `catalogue.tracks` (PostgreSQL refuse de vider une table référencée) ; sur le staging, la tâche de minuit génère des défis que le prochain import doit pouvoir effacer. L'historique des défis sera importé en E4.
- **Tests** : `UnitTests/Daily` (`CooldownSeededSelectorTests` : tirage, déterminisme, ordre des candidats, doublons, cooldown, pool insuffisant ; `DailyChallengeTests`), `IntegrationTests/Daily` (`GenerateChallengeTests` : tirage, même défi pour la même graine, déjà présent, cooldown aux limites de la v1 et réglage relu à chaud, morceaux désactivés / sans extrait / inconnus jamais tirés, pool insuffisant et regarni, nombre de morceaux réglable, **course entre générations**, tâches (compte rendu, exception, réessais), clé étrangère ; `TrackUsageTests` : usage calculé, limite du cooldown, jour de jeu, pool admin ; `GenerateTodayButtonTests` : bouton, suivi de l'exécution, échec, 401/403), `Testing/E2eHostTests` (seed par de vrais défis, `generate-today`), `Jobs/ScheduledJobsTests`, règles d'architecture.

### Parties (E2)

Les parties d'un joueur sur le défi du jour, leur score, sa série et ses gels. **Daily n'utilise des autres modules que leurs `Contracts`** : `Players/Contracts` (`ICurrentPlayer`, `IPlayerDirectory` : le joueur a-t-il un compte), `Catalogue/Contracts` (`ITrackDirectory`, `ITrackPreviews` : l'extrait des morceaux, ajouté en E2), `Gameplay/Contracts` (`TrackRound`, `HintPolicy`, `IHintProvider`, `IAnswerMatcher`). Les clés étrangères vers `players.players` sont déclarées **par le nom du type** (comme celle vers `catalogue.tracks`) : une **constante** portant ce nom compte comme une dépendance pour NetArchTest, le nom s'écrit en littéral ; et `InSecondsDbContext` applique les configurations de **Players et Catalogue d'abord** (EF ne retrouve une entité par son nom que si elle est déjà dans le modèle, sinon il en crée une autre sans erreur).

- **Tables** (schéma `daily`, migration `DailySessions`) : `sessions` (`id` tiré d'une séquence HiLo `sessions_hilo`, unique `(player_id, challenge_id)` : `ix_sessions_player_challenge`, index `(challenge_id, status)`, `status` 0 en cours / 1 terminée / 2 abandonnée / 3 expirée avec un CHECK, `current_position` / `current_listened_seconds` / `current_hint_level` : le verrou du morceau en cours, `freezes_used` / `freeze_earned` : l'effet de la complétion sur les gels), `answers` (PK `(session_id, position)` : une réponse par morceau, jamais deux ; `answered_at` vide pour l'historique repris) et `streaks` (`player_id`, `current_streak`, `last_played_date`, `freezes` ; pas de ligne = aucune série). Les réponses saisies sont gardées (v1), jamais journalisées.
- **Domaine** (`Domain/`) : `DailySession` (`Start`, `TurnOf(position, nombre réel de morceaux)`, `RoundOfCurrentTrack(politique)` qui reconstitue la `TrackRound` et **borne le niveau d'indice à la politique**, `KeepRound`, `Answer` qui libère le verrou et termine la partie sur le nombre réel de morceaux, `Abandon`, `Expire`), `SessionAnswer`, `DailyStreak` (`RecordCompletion(date du défi, compte lié ?, règles)`, `GrantAccountCreationFreeze`, `View` / `Compute` : la série effective d'un jour, protégée ou cassée, sans rien écrire), `IDailyScoringPolicy` / `DurationScoringPolicy` (barème de la v1), `TrackAnswerStats` (ce que la révélation montre des autres joueurs).
- **Réglages** (`DailyOptions`, `IOptionsMonitor`, relus à chaud, défauts de la v1) : `Daily:GuessTimerSeconds`, `AllowedDurationsSeconds`, `DurationScores` (liste d'objets `{ seconds, score }`), `HintUnlockDurationsSeconds`, `HintPenaltyPercent` (`{"1":30,"2":60}`), `StreakFreezeEveryDays`, `StreakFreezeMax`, `StreakLostNudgeMinDays`. **Aucune valeur initiale sur les listes et les dictionnaires** : le binder les AJOUTE aux éléments lus ; les défauts sont dans les propriétés `Effective…`. `DailyRules` (singleton) en tire à chaque appel la politique d'indices (bornée aux `IHintProvider` contigus depuis le niveau 1, repli sur les seuils de la v1 si les siens ne sont pas croissants ; l'erreur au journal n'est écrite qu'une fois par valeur), les paliers (un palier que `numeric(4,2)` ne garderait pas tel quel fait retomber sur ceux de la v1), le barème, les paliers, les règles de gel ; `DailyOptionsStartupCheck` **refuse de démarrer** si les réglages sont incohérents (plus de niveaux d'indice que de fournisseurs, seuils non croissants, paliers ou pourcentages aberrants) : au démarrage seulement, un réglage changé à chaud ne fait pas tomber les parties en cours.
- **Routes** (`Application/`, Wolverine.Http en étapes `LoadAsync` / `Validate` / `Post`). Un morceau se désigne par sa **position** (1 à N). Le morceau en cours est toujours le premier sans réponse (piège 35).

- **Série** : lue puis écrite par la complétion et par le gel offert, sous un verrou consultatif par joueur (`LockStreakAsync`, avant `FindStreakAsync`) : deux créations simultanées de la ligne se suivent au lieu de se heurter sur la clé primaire.
- **Fin de partie** (`SubmitAnswerEndpoint.Post`, une seule transaction) : la réponse, le score, et, sur le dernier morceau **réel** du défi (piège 38), le statut, la série et les gels, **sur la date du défi** (piège 18). Les gels ne sont consommés ou gagnés que par un **compte** (`IPlayerDirectory`). - **Wolverine** : un paramètre chargé par `LoadAsync` qui n'est pas le corps de la requête porte `[NotBody]` (sinon Wolverine tente de le lire dans le corps, 400 sans message) ; **un service concret** (`DailyRules`) aussi, quand il est le seul paramètre complexe après lui.

## Module Gameplay (`Modules/Gameplay/`, D1)

La mécanique d'un morceau, partagée par les modes (§ 3.1 et 5.4 du plan) : **de la logique pure, sans table, route ni réglage**. Point d'entrée `GameplayModule.AddGameplay()` (singletons : `IAnswerMatcher`, `ISeededShuffle`, un `IHintProvider` par niveau). Ne dépend que de `Catalogue/Contracts` (en fait de rien pour l'instant) et reste sans accès aux données ni au web : testé par `ArchitectureTests` (`Gameplay_NeDependQue…`, `LesModulesDesNoyaux_NeDependentPasDeGameplay`). **Tout ce qu'un mode utilise est dans `Contracts/`** (un mode n'utilise d'un autre module que ses contrats) ; `Domain/` ne contient que les implémentations.
- **`TrackRound`** (objet valeur immuable, `Contracts/`) : ce que la manche garde, **ni le morceau ni les points**. `Start`, `Resume(listenedSeconds, hintLevel)` (le mode range ces deux nombres dans sa session et reconstitue la manche : Daily, `current_listened_seconds` et `current_hint_level`), `Listen(seconds)`, `RevealHint(level, policy)`, `Answer(claimedSeconds, artist, title, expected, matcher)`. Identité du morceau et verrou (piège 35) : l'affaire du mode.
  - **Plancher d'écoute** (piège 35) : `Listen` garde le **maximum** (écouter moins, rejouer, recharger la page ne le réduit jamais). `Answer` **refuse** (`AnswerResult.BelowFloor(plancher)`) un palier annoncé inférieur au plancher : écouter longuement ou débloquer un indice puis annoncer un palier court pour gagner plus. Un morceau sans extrait (palier 0, jamais écouté) n'a pas de plancher.
  - **Indices** : `RevealHint` refuse un niveau que la politique du mode ne propose pas (`UnknownLevel`) ou dont le seuil n'est pas atteint (`NotUnlocked`, avec `UnlocksAtSeconds`). Le niveau garde son **maximum** (redemander un niveau plus bas est accepté, rien ne redescend) ; **écouter plus ne révèle rien et ne remet rien à zéro** (règle v1 : seul le clic explicite révèle, et ce qui est révélé reste). Le niveau d'indice n'est jamais fourni par le client : il vient de la manche, que le mode relit de sa session.
  - **`RoundOutcome`** : `ArtistCorrect`, `TitleCorrect` (corrigés séparément, le score partiel du mode en dépend), le palier annoncé et le niveau d'indice révélé ; `FoundBoth`, `FoundAny`. **Aucun point** : le calcul appartient au mode (`IDailyScoringPolicy`, E).
- **`HintPolicy`** (propre à chaque mode) : les durées d'écoute qui débloquent les niveaux (`new HintPolicy([5m, 10m])`), **strictement positives et croissantes** (refusé sinon, la v1 ne validait rien). `HintPolicy.None` : un mode sans indice. Daily la construira de ses réglages (E).
- **`IHintProvider`** (un par élément révélé) : `YearHint` (niveau 1, année, valeur `null` si inconnue, format invariant) et `HangmanArtistHint` (niveau 2, artiste « pendu » : première lettre de chaque mot, lettres et chiffres masqués, ponctuation gardée, mots séparés par 3 espaces ; un nom sans mot donne un motif vide). `HintFacts.UpTo(level, providers, subject)` : **cumulatif** (le niveau 2 rend aussi l'année), dans l'ordre des niveaux. Un indice de plus (décennie, genre) = un fournisseur de plus, sans toucher à `TrackRound`.
- **`FuzzyAnswerMatcher`** (`IAnswerMatcher`, ex-`TextNormalizer`) : insensible à la casse, aux accents, aux parenthèses et crochets, à la ponctuation et aux mots vides (`the le la les un une de du des and et feat ft vs`), puis distance de Levenshtein ≤ **min(2, longueur de la référence ÷ 3)** (moins de 3 caractères : égalité stricte ; 3 à 5 : une faute) : calculée sur la **référence**, pas sur la saisie (l'allonger ne gonfle pas la tolérance). `FuzzyAnswerMatcher(maxTypos)` pour une autre tolérance. Reprise à l'identique de la v1, cas limites compris. **Ajouts** : une saisie de plus de 600 caractères (`MaxInputLength`, le double des limites de l'API) est refusée sans être lue (la v1 la traitait, coût quadratique sur des « ( » non fermées), et la distance n'est pas calculée quand l'écart de longueur dépasse déjà le seuil. Une référence faite de mots vides (« The The ») se normalise en chaîne vide et n'est égalée que par une saisie qui se normalise pareil.
- **`FisherYatesShuffle`** (`ISeededShuffle`) : Fisher-Yates à graine, **même ordre que l'algorithme de la v1** pour une même graine et une même liste (testé contre une copie de l'algorithme de la v1, et un ordre épinglé : changer l'algorithme changerait les morceaux d'une date déjà annoncée). La liste reçue n'est pas modifiée. `Random(graine)` est voulu : la graine est publique (le numéro du jour), tout le monde joue le même défi.
- **Tests** (`UnitTests/Gameplay`, 134 tests) : correction (cas de la v1, accents, ponctuation, mots vides, seuil par longueur, tolérance configurable, cas vides), manche (plancher, indices, cumul, politique, correction, parcours « écouter plus après un indice »), indices (année, pendu, cumul, politique de déblocage), tirage (déterminisme, permutation, pas de biais de position, ordre épinglé).

## Import v1 → v2 (`deploy/migration-v2/`, depuis B4)

Mode d'emploi complet : [`deploy/migration-v2/README.md`](../../../deploy/migration-v2/README.md). Construit module par module (B4 Players, C2 Catalogue, E4 Daily, G1 complet). Parties faites : Players (B4), Catalogue (C2) et Daily (E4).

Rejouable (chaque partie vide d'abord ses tables v2). Prérequis : migrations v2 appliquées (`--migrate-only`).

Séquences `challenges_hilo` et `sessions_hilo` remises au-delà du plus grand identifiant. Pré-contrôles nommant la partie ou le joueur (réponse d'un autre défi, valeurs hors des colonnes). `20-verify.sql` relit tout contre la v1 : lignes, défis, morceaux des défis, parties (champ par champ, règle recalculée sur les réponses de la v2), parties en cours reprenables, réponses, scores (par défi, par joueur, par partie terminée), séries, séquences ; **écarts de cooldown et de rang Deezer figé listés sans bloquer** (`LastUsedDate` et `UsageCount` de la v1 comparés au calcul sur les défis, que seule la v2 lit).
