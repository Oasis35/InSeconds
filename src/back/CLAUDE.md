# CLAUDE.md - back

Back d'InSeconds (`src/back`), en prod et sur le staging. Vue d'ensemble, conventions et pièges : [`CLAUDE.md`](../../CLAUDE.md) racine. Ce fichier détaille le code tel qu'il est ; toute PR qui change le back le met à jour.

État : les quatre modules (`Players`, `Catalogue`, `Gameplay`, `Daily`) et l'admin du jeu du jour sont complets. La reprise des anciens cookies (`legacy_tokens`, `LegacyCookieTransitionMiddleware`, anciennes clés Data Protection) sera retirée vers le 14/01/2027 (#237). Le module `Runs` a son socle (défi, tirage par difficulté, accès), ses routes de jeu (la partie, jauge, neutralisation, fin, record) et la comparaison des joueurs d'une playlist (cf. « Module Runs ») ([`docs/runs/`](../../docs/runs/README.md)). Module `Players` : invités, appareils, cookie standard validé en base, reprise des anciens cookies, clés Data Protection chiffrées par certificat, connexion par lien magique et dev-login, pseudo, changement d'email, déconnexion, liste et révocation des appareils, droits RGPD et purge nocturne (cf. « Authentification » et « Module Players »). Module `Catalogue` : morceaux du pool (renommer, désactiver, contrôler l'extrait, rang), client Deezer découpé en ports avec cache (`InSeconds.Deezer`), recherche publique, routes admin du pool, tâche `catalogue-refresh`, faux Deezer dans l'hôte de test (cf. « Client Deezer » et « Module Catalogue »). `Daily` : les défis, leur génération (nocturne, à la volée), l'usage des morceaux calculé sur les défis, les parties, le score, la série et les gels, les statistiques et l'admin (cf. « Module Daily »). `Gameplay` : la mécanique d'un morceau.

## Commandes

```bash
cd src/back
dotnet build InSeconds.slnx
dotnet test --solution InSeconds.slnx      # unitaires + architecture + intégration (Docker requis)
dotnet run --project InSeconds.Api          # http://localhost:5175
dotnet run --project InSeconds.Api -- --migrate-only   # applique les migrations puis rend la main
dotnet run --project InSeconds.Api -- --rotate-data-protection-key   # crée une clé Data Protection neuve (après une copie de base)
dotnet run --project InSeconds.Api -- --freeze-day-stats   # fige les stats des jours terminés sans photo
dotnet run --project InSeconds.Api.Testing  # hôte de test (Development) : API + /api/e2e + faux email + faux Deezer

# Image de prod (contexte src/back), sans l'hôte de test
docker build -f InSeconds.Api/Dockerfile -t inseconds-api .

# Régénérer le code Wolverine (après tout ajout ou changement de handler / endpoint), puis commiter
rm -rf InSeconds.Api/Internal/Generated && dotnet run --project InSeconds.Api -- codegen write

# Nouvelle migration (depuis src/back/InSeconds.Api)
dotnet ef migrations add <Nom> --output-dir Infrastructure/Persistence/Migrations
```

`global.json` fixe le lanceur de tests **Microsoft.Testing.Platform** (`test.runner`) : avec le SDK .NET 10, `dotnet test` refuse l'ancien mode VSTest pour xUnit v3. D'où `dotnet test --solution …` (et non `dotnet test InSeconds.slnx`).

Les modules métier vivent dans `InSeconds.Api/Modules/<Module>/` (`Players`, `Catalogue`, `Gameplay`, `Daily`, `Runs`) ; un module n'utilise des autres que leur dossier `Contracts` (vérifié par `ArchitectureTests/ModuleDependencyTests`, qui s'applique dès qu'un module existe). Le dossier `InSeconds.Api/Infrastructure` est transverse et ne connaît aucun module, sauf la composition et les points d'entrée nommés dans `ArchitectureTests/InfrastructureDependencyTests` (`ApiComposition`, `WolverineSetup`, `PlayerDataCommand`, `FreezeDayStatsCommand`) : ce qui est propre à un module vit dans le module.

## Règles

- **Rien dans le schéma `public`** (vide). Chaque entité déclare son schéma (`infra`, puis un schéma par module). L'historique EF est `infra.__ef_migrations_history`. Vérifié par `PersistenceTests` et `DatabaseTests`.
- **Noms en snake_case** (`EFCore.NamingConventions`).
- **`citext` vit dans le schéma `extensions`** (pas dans `public`). Ses opérateurs, dont `=`, n'y sont trouvés que si `extensions` est dans le `search_path` : `DatabaseServiceCollectionExtensions.WithExtensionsSearchPath` l'ajoute à la chaîne de connexion. Sans lui, PostgreSQL compare en `text`, sensible à la casse, sans aucune erreur. Toute connexion ouverte hors du `DbContext` sur une colonne `citext` doit passer par cette méthode.
- **Jamais `DateTime.UtcNow`/`Now`/`Today`** (ni `DateTimeOffset`) dans `InSeconds.Api` : l'heure vient de `TimeProvider` ou d'`IGameCalendar` (`Now`, `Today`, `StartOf(jour)`), remplaçables en test par `FakeTimeProvider`. Vérifié par `ClockUsageTests` (scan des sources).
- **Erreurs** : toute réponse d'erreur est un ProblemDetails avec `code` (`ErrorCodes`, ex. `common.not_found`) et `traceId` (32 hex, recherchable dans Grafana). Sur un 500, titre générique, ni `detail` ni exception. Chaque module a ses codes (`PlayersErrorCodes`, `CatalogueErrorCodes`, `DailyErrorCodes`/`DailyAdminErrorCodes`) ; **ne jamais renommer un code publié** (le front les traduit).
- **Handlers** (vérifié par `ArchitectureTests/HandlerRulesTests`) : **jamais de `SaveChanges`** hors du code généré par Wolverine, qui enregistre la transaction. Quatre exceptions écrites, hors de toute transaction de Wolverine : `SettingsStore.SetAsync` (le rechargement des réglages doit lire la ligne enregistrée ; la route du cooldown qui l'appelle est `[NonTransactional]`), `EfPlayerSessions.OpenFromLegacyTokenAsync` (middleware de reprise des anciens cookies), `EfCatalogueStore.SaveAlbumGenresAsync` (contrôle nocturne `[NonTransactional]` : un album à la fois, son propre enregistrement, jamais une transaction ouverte pendant les pauses) et la commande `--freeze-day-stats`. Une nouvelle exception s'ajoute à la liste du test et ici. **Jamais d'`IResult`** : une route Wolverine renvoie un résultat métier (ou rien, avec `[EmptyResponse]` pour un 204), les erreurs sont des `ProblemDetails` rendus par ses étapes (`Validate`, `Before`) ; aucun type `Result<T, Error>`. Seule la route hors Wolverine `/health` utilise `Results`. **Un noyau (Players, Catalogue) ne voit d'un mode que ses `Contracts`** (seule exception nommée : Players → `Daily.Contracts.IStreakGrants`, cf. `ModuleRules.NamedExceptions` ; le sens normal est l'inverse, un mode **implémente** un contrat du noyau : `IPlayerDataContributor`, `ITrackUsage`).
- **Tests** : `Assert` de xUnit uniquement (pas de FluentAssertions, licence payante depuis la v8). Une base neuve par classe de tests d'intégration (`PostgresFixture.CreateDatabaseAsync`), un seul conteneur pour toute la suite. Cette base est la **copie d'une base modèle** (`CREATE DATABASE … TEMPLATE`), préparée une fois au début de la suite par le démarrage d'une API (migrations, tables de Wolverine et de Hangfire), puis vidée de ce que cette API y a laissé (tables de `messaging`, clé Data Protection) : chaque classe rejouait sinon tout cela. Les tests du premier démarrage et des migrations (`DatabaseTests`, `MigrateOnlyTests`) prennent une base vide (`CreateEmptyDatabaseAsync`). Chaque piège du CLAUDE.md racine qui touche le back garde un test nommé `PiegeNN_…` (ou `…_PiegeNN`), retrouvable par son numéro : 14, 16, 18, 21, 22, 27, 30, 31, 35, 37, 38, 39. Le 19 (`Task.Delay` réveillé avant minuit) ne s'applique plus : les tâches nocturnes sont planifiées par Hangfire.

## Réglages (`infra.settings`)

Une ligne par réglage : `key` = chemin de configuration complet (`Daily:GuessTimerSeconds`), `value` en `jsonb`. `DatabaseSettingsConfigurationProvider` lit la table et l'aplatit dans `IConfiguration` (`SettingsJsonFlattener` : objet → `clé:propriété`, tableau → `clé:0`, `clé:1`…). Les modules lisent leurs options par `IOptionsMonitor<T>` : **tout est relu à chaud**, sans redémarrage.

- Écrire un réglage : `SettingsStore.SetAsync(key, value)` (upsert puis rechargement).
- Après une écriture SQL directe : `ISettingsReloader.Reload()`.
- Le provider ignore seulement « base, schéma ou table absents » (premier démarrage avant migration) ; toute autre erreur SQL empêche le démarrage.
- **Pas de clé de dictionnaire décimale** : le binder .NET laisse un `Dictionary<decimal, …>` vide sans erreur. D'où `DurationScores` stocké en liste d'objets `[{"seconds":0.5,"score":1000},…]`. Les clés `string`, entières ou `enum` fonctionnent (`HintPenaltyPercent` : `{"1":30,"2":60}` → `Dictionary<int,int>`).

## Démarrage

`Program.cs` appelle `ApiComposition.AddInSecondsApi(args)` puis `UseInSecondsApi()`, partagés avec l'hôte de test. Services : réglages en base → OpenTelemetry → `DbContext` → migrations → calendrier → ProblemDetails → health checks → Data Protection → auth → proxies de confiance → rate limiting → email → client Deezer → Wolverine → Hangfire → `App:PublicUrl` → modules (`AddPlayers`, `AddCatalogue`, `AddGameplay`, `AddDaily`). Pipeline : `UseForwardedHeaders` (en premier : tout le reste voit l'IP réelle) → en-têtes de sécurité → erreurs → CORS → authentification → reprise des anciens cookies → télémétrie du joueur (`UsePlayerTelemetry`) → autorisation → rate limiter → routes (dont le tableau de bord `/jobs`). Puis `RunJasperFxCommands(args)` (démarre l'API, ou exécute une commande Wolverine comme `codegen write`). Les migrations passent par `DatabaseStartupService` (`IHostedLifecycleService.StartingAsync`) : avant le démarrage de Wolverine et Hangfire, sauf si `Database:MigrateOnStartup=false` ; les réglages sont rechargés juste après (la table peut ne pas avoir existé à la construction de la configuration). Une commande Wolverine ne démarre pas l'hôte : pas de migration, et pas de lecture des réglages en base (`CommandLine.StartsServer`), pour que la CI génère le code sans base.

`--migrate-only` (`MigrateOnlyCommand`) : hôte minimal (base seulement, ni serveur web ni tâche de fond), applique les migrations et rend la main avec le code 0. Sert au déploiement et à la copie prod → staging.

`--freeze-day-stats` (`FreezeDayStatsCommand`) : hôte minimal (base, réglages lus en base, calendrier, règles du jeu et fournisseurs d'indices ; ni serveur, ni Wolverine, ni Hangfire), refuse de figer quoi que ce soit (code 1) si les réglages ne passent pas le contrôle du démarrage de l'API (`DailyOptionsChecks.Problems`), fige les statistiques de **tous les jours terminés (J-2 et avant) sans photo**, du plus ancien au plus récent, par `CloseChallengeDayHandler.Handle` (la règle de la tâche `daily-close-day`), **une transaction par jour** (le verrou du jour en demande une). Un jour qui échoue n'empêche pas les suivants : code de sortie 1 à la fin. Rejouable. À lancer après l'import complet (les paliers et le barème figés sont ceux des réglages).

`--export-player <email>` et `--delete-player <email>` (`PlayerDataCommand`, RGPD) : commandes de secours pour une demande reçue par email d'un joueur qui ne peut plus se connecter (le profil a ses boutons). Hôte minimal (base, réglages, `ITrackDirectory`, les contributeurs des modes par `ApiComposition.AddPlayerDataContributors`, la même liste que l'API, stores de Players ; ni serveur, ni Wolverine, ni Hangfire). L'adresse est normalisée comme à la connexion. `--export-player` écrit le JSON de `PlayerDataExporter` (le même que `GET /api/players/me/export`) sur la **sortie standard** ; `--delete-player` appelle `AccountErasure` dans une transaction. Journaux sur la **sortie d'erreur** (jamais mêlés au JSON), sans adresse. Codes de sortie : 0, 2 (aucun compte n'a cette adresse), 64 (adresse manquante). Le cache de validation des cookies vit dans le processus de l'API : un appareil d'un compte supprimé par la commande y est refusé au plus une minute plus tard. Mode d'emploi sur le VPS : `docs/exploitation/deploiement.md`, « Commandes utiles VPS ».

`--rotate-data-protection-key` (`RotateDataProtectionKeyCommand`) : même principe (base et Data Protection seulement, le host n'est jamais démarré), crée par `IKeyManager.CreateNewKey` une clé active tout de suite, valable 90 jours, chiffrée par le certificat (exigé en prod et en staging). Lancée par la copie prod → staging (`deploy/vps/copy-prod-db-to-staging.sh`), après l'anonymisation qui vide les clés.

## Wolverine (`Infrastructure/Messaging/WolverineSetup.cs`)

- Endpoints en **Wolverine.Http** (`[WolverineGet]`…), validation FluentValidation en ProblemDetails. Toute route `/api/admin*` reçoit la policy Admin (`ConfigureEndpoints`) : impossible d'oublier l'attribut.
- **Service location** interdite par défaut (le code généré construit lui-même les dépendances, d'où des implémentations publiques) ; seules exceptions (`AlwaysUseServiceLocationFor`, liste exacte dans `WolverineSetup`) : `ITrackPoolUsage`, `IDailyTrackUsage`, `PlayerDataExporter` et `AccountErasure` (ils énumèrent les `IPlayerDataContributor`, que le code généré ne sait pas construire), `SettingsStore`, `IStreakGrants` (remplacé par les tests, cf. « Codegen statique »), `IEmailSender`, choisi au démarrage par une fabrique (Brevo, redirigé, capturé), et les ports Deezer (`IPreviewProvider`, `ITrackSearch`, `ITrackMetadataSource`, `IAlbumSource`, `CachedTrackSearch` : client HTTP typé et décorateur enregistrés par fabrique, cf. « Client Deezer »).
- `AutoApplyTransactions` + transactions EF Core : un handler qui modifie le `DbContext` et publie un message fait **une seule transaction** (donnée + outbox). Messages durables dans le schéma **`messaging`** (`PersistMessagesWithPostgresql(cs, "messaging")`, files locales durables). Vérifié par `Messaging/OutboxTests` : message envoyé seulement si la donnée est enregistrée, et aucun message ni enveloppe sinon.
- **Les tables de `messaging` sont créées par Wolverine au démarrage, pas par les migrations EF.** `MapWolverineEnvelopeStorage("messaging")` ne fait que les déclarer au `DbContext` (exclues des migrations ; la migration `MapWolverineEnvelopeStorage` est vide exprès). `--migrate-only` ne les crée donc pas.
- **Codegen statique** : en Production et Staging, `TypeLoadMode.Static` (`WolverineSetup.UsesStaticCodegen`) ; le code est lu dans `Internal/Generated`, commité. **En test** (`Testing` : tests d'intégration, hôte des E2E), `TypeLoadMode.Auto` sans écriture de fichier (`UsesPreBuiltCodeWhenPresent`, `SourceCodeWritingEnabled = false`) : le code commité est relu, seuls les handlers absents (ceux des tests et de l'hôte de test) sont compilés au démarrage ; chaque API de test recompilait sinon tous les handlers (la moitié du temps de calcul de la suite, et jusqu'à 14 Go de mémoire). Le code commité doit donc être à jour avant de lancer les tests, et **un service que les tests remplacent doit être en service location** (sinon le code commité le construit en dur et le remplacement est ignoré : `IStreakGrants`, remplacé par `RecordingStreakGrants`). En développement, génération à la volée (`UseRuntimeCompilation`). Oublier de régénérer = l'API refuse de démarrer en staging (`MissingPreBuiltTypesException`, testé par `StaticCodegenTests`) ; le job CI `back` supprime le dossier, relance `codegen write` et échoue si le résultat diffère du dépôt. `codegen write` ne supprime pas les fichiers périmés : toujours `rm -rf` avant.

## Tâches planifiées (Hangfire, `Infrastructure/Jobs/`)

- Stockage PostgreSQL dans le schéma **`jobs`** (créé par Hangfire au démarrage, comme `messaging`). Serveur de tâches si `Jobs:Server:Enabled` (défaut `true`, `false` dans les tests d'intégration), `Jobs:Server:WorkerCount` (défaut 2 : peu de tâches, et chaque worker tient une connexion).
- **Déclarer une tâche** : une classe `IScheduledJob` (`RunAsync` renvoie un résultat sérialisé en JSON, ou `null`), enregistrée par `services.AddScheduledJob<TJob>("id", Cron.Daily())`. Planning surchargeable par `Jobs:<id>:Cron`, fuseau UTC. `RecurringJobsRegistrar` enregistre les tâches au démarrage et **supprime celles qui ne sont plus déclarées**. Ajouter la tâche à `ExpectedJobs` de `Jobs/ScheduledJobsTests` (aujourd'hui : `catalogue-refresh`, `players-purge-expired-tokens`, `daily-generate-challenge`, `daily-close-day`).
- **Lancer une tâche à la demande** : depuis `/jobs` (« Tâches récurrentes », « Déclencher maintenant »). L'admin n'a pas de bouton pour cela : l'onglet Actions montre le dernier passage de chaque tâche.
- **Compte rendu** : une tâche qui rend un objet voit ses propriétés à zéro absentes du JSON (Hangfire), et un `$type` : rendre un dictionnaire (`PreviewRefreshResult.ToReport()`) pour avoir toutes les clés.
- **Échec métier** : lever `JobFailedException("module.code")` ; le code est renvoyé tel quel. Toute autre exception est rendue en `common.unexpected` (ni message ni pile exposés).
- **Tableau de bord `/jobs`** : policy Admin (401 anonyme, 403 joueur), `Authorization = []` (le filtre par défaut de Hangfire n'accepte que localhost), jeton antiforgery exigé sur ses actions (S3). Pas de Cloudflare Access, ni en prod ni au staging : la policy Admin suffit (cf. `docs/architecture/decisions.md`).
- **`GET /api/admin/jobs/last-runs`** (`getJobLastRuns`, `GetJobLastRunsEndpoint`) : pour chaque tâche récurrente (triées par identifiant), `JobLastRun { id, state, at, result, errorCode, retryAt, nextRunAt }`. `state` : `queued`, `processing`, `succeeded`, `failed`, `retry_scheduled`, `deleted`, vide si aucun passage connu ; `at` : heure de l'échec pour `failed` et `retry_scheduled`, sinon de l'état courant ; `result` (JSON) si réussie ; `errorCode` si échouée ; `retryAt` : prochain essai ; `nextRunAt` : prochain passage planifié (vide pour une tâche en pause). Dates en UTC.
- **Surveillance par healthchecks.io** (#315) : `JobHeartbeatFilter` (posé sur le serveur Hangfire par `options.FilterProvider`, **pas** dans `GlobalJobFilters` : il dépend des services de l'API, et la liste globale est partagée par toutes les API de test du processus) appelle `JobHeartbeat` après chaque exécution d'une tâche récurrente (paramètre Hangfire `RecurringJobId`, donc aussi un lancement depuis `/jobs`) : `POST <Healthchecks:BaseUrl>/<Healthchecks:PingKey>/<id>?create=1` si réussie, `…/<id>/fail?create=1` si échouée (y compris un essai raté suivi d'un nouvel essai) ; rien si le serveur s'arrête (`Canceled`). Sans `Healthchecks:PingKey` (dev, tests), rien n'est envoyé ; le staging a sa propre clé (projet healthchecks.io séparé « [Dev]InSeconds », `.env.staging`), jamais celle de la prod. Jamais bloquant (délai 10 s, `JobsSetup.HeartbeatTimeout`) : un échec du signal donne un `Warning` sans la clé (secrète, jamais journalisée, ni l'adresse). Tests : `UnitTests/Infrastructure/Jobs/JobHeartbeatTests`, `JobLastRunsTests` (`…SignalDeReussiteAHealthchecks`, `…SignalFailAHealthchecks`).
- **Rétention** : Hangfire garde une exécution terminée **7 jours** (`JobsSetup.ExecutionRetention`, `WithJobExpirationTimeout` ; 1 jour par défaut) : c'est ce que relisent `/jobs` et les témoins de l'admin. Au-delà, le dernier passage est inconnu (`state` vide). Allonger ce délai garde plus de lignes dans `jobs.job`.
- **Tests avec un vrai serveur Hangfire** (`Jobs:Server:Enabled=true`, ex. `JobLastRunsTests`) : dans la collection `HangfireServerCollection`, qui passe seule. Hangfire garde son activateur de tâches en global : une autre API de test créée puis détruite en parallèle le remplace, et la tâche échoue sur un `IServiceProvider` détruit (vu en CI).

## Services transverses (`InSeconds.Infrastructure`)

Projet sans dépendance vers l'API ni les modules (vérifié par `ArchitectureTests/ProjectDependencyTests`). L'API l'utilise par ses méthodes d'extension.

- **Emails** (`Email/`) : les modules dépendent de `IEmailSender` seulement. `BrevoEmailSender` (API transactionnelle Brevo, `Brevo:ApiKey`/`SenderEmail`/`SenderName`, vérifiés au démarrage en Production et Staging). Si `EmailRedirect:To` est renseigné, `RedirectingEmailSender` envoie tout à cette adresse avec un bandeau (objet inchangé) ; **obligatoire en Staging** (l'API refuse de démarrer sans, `EmailStartupTests`). Journaux : sujet et identifiant Brevo (EventId 1007/1101), **jamais l'adresse**, ni celle que le message d'erreur Brevo pourrait citer.
- **OpenTelemetry** (`Observability/`) : service `inseconds-api` ( ASP.NET Core, HttpClient, Npgsql, Wolverine, runtime ; logs avec scopes). ## Authentification (`Modules/Players/Auth/`)

Cookie standard d'ASP.NET Core. L'authentification du joueur appartient au module Players (`InSeconds.Api.Modules.Players.Auth`) : les autres modules n'en voient que `ICurrentPlayer` (`Players/Contracts`). Restent transverses, dans `Infrastructure/Auth/` : `DataProtectionSetup` et les noms `AuthorizationPolicies.Admin` / `Roles.Admin`, que la composition applique aux routes sans connaître Players.

- **Cookie** (`AuthSetup`) : `__Host-inseconds` (`Secure`, `SameSite=Lax`) en prod et en staging, `inseconds` (`SameSite=Strict`, sans `Secure`) en développement et en test ; `HttpOnly`, persistant, 90 jours glissants. 401/403, jamais de redirection (`PlayerCookieEvents`).
- **Ticket** (`PlayerClaims`) : `player_id` et `device_session_id` seulement. Le rôle admin n'y est ni écrit ni lu : la validation le relit en base et ne l'ajoute qu'au joueur de la requête.
- **Validation à chaque requête** (`PlayerCookieEvents.ValidatePrincipal` → `DeviceSessionValidator`) : appareil existant, non révoqué, joueur non supprimé, rôle admin relu en base. Résultat gardé **une minute** dans un cache dédié (`DeviceSessionStatusCache`, pas l'`IMemoryCache` partagé : piège 24), fraîcheur jugée sur `TimeProvider` : une révocation ou un retrait du rôle s'appliquent en moins d'une minute. Dernière visite (appareil et joueur) notée au plus **toutes les 5 minutes** (R17). Appareil invalide : cookie supprimé, requête anonyme. **Erreur de base : 500, jamais de déconnexion** (piège 37).
- **Joueur courant** : `ICurrentPlayer` (`Modules/Players/Contracts`), lu dans les claims par `ClaimsCurrentPlayer`. Pose et retrait du cookie : `IPlayerSignIn` (`SignInAsync`, `SignOutAsync` ; le changement est visible dès la suite de la requête). Une session révoquée est retirée du cache de validation par `IDeviceSessionValidationCache.Forget` : refusée dès la requête suivante (S5). `Forget` la retire tout de suite **puis une seconde fois au démarrage de la réponse** (`Response.OnStarting`), donc après le commit de Wolverine, qui précède toujours l'écriture de la réponse ; et le cache compte les oublis (`Generation`) : un état lu en base n'est gardé que si aucune session n'a été oubliée depuis le début de sa lecture (`TrySet`). Une requête concurrente qui a lu la session encore active avant le commit ne peut donc plus la remettre en cache (#319). Tests : `UnitTests/Players/DeviceSessionValidatorTests` (`RevocationPendantLaLecture_…`, `Revocation_OublieAussiAuDemarrageDeLaReponse_…`).
- **Origine de confiance** (`TrustedOrigins`, piège 22) : `Origin`, ou à défaut l'autorité exacte du `Referer` (jamais un préfixe), dans `Cors:AllowedOrigins` + `Auth:TrustedOrigins` (fronts locaux servis par le proxy d'`ng serve`, sans CORS). Ni l'un ni l'autre : refusé. Exigée par la vérification du lien magique seulement (seul `POST` public qui pose un cookie à partir d'un secret). `ApiFactory` des tests y met `http://localhost:5176` (`ApiFactory.FrontOrigin`).
- **Reprise des anciens cookies** (`LegacyCookieTransitionMiddleware`, juste après l'authentification) : ancien cookie `authToken` déchiffré avec ses paramètres d'origine (application `InSeconds`, purpose `InSeconds.Auth.Cookie`, R10), jeton haché (`LegacyToken.HashOf` : SHA-256 du Guid en minuscules avec tirets, en UTF-8, le même calcul que l'import) et cherché dans `players.legacy_tokens` (S6). Trouvé : **une session d'appareil par conversion** (tous les appareils d'un compte partageaient ce jeton, R1) et cookie standard. Un même jeton converti depuis moins d'une minute retrouve la session qu'il vient d'ouvrir (`LegacyConversionCache`, conversions d'un même jeton faites l'une après l'autre) : les requêtes parallèles du premier chargement ne créent qu'une session, et un ancien cookie rejoué en boucle n'en crée qu'une par minute ; deux appareils du même compte convertis dans la même minute partagent leur session (rare, sans danger). Tests : `LegacyCookieTests`, `UnitTests/Players/LegacyConversionCacheTests`. L'ancien cookie est toujours supprimé, sauf sur une erreur de base (piège 37). Un cookie standard valide l'emporte.
- **Data Protection** (`DataProtectionSetup`) : application `InSeconds`, clés dans `infra.data_protection_keys`. Chiffrées par le certificat `DataProtection:CertificatePath`/`CertificatePassword` (S16, `ProtectKeysWithCertificate` + `UnprotectKeysWithAnyCertificate`), **exigé quand l'API démarre en prod et en staging** (pas pour `codegen write`). En développement et en test, sans certificat, les clés restent en clair.
- **Policy `Admin`** : joueur authentifié avec le rôle `admin`, posée sur tout `/api/admin` (`WolverineSetup`) et sur `/jobs`. Antiforgery enregistré (actions du tableau de bord Hangfire).
- **Tests** : `TestAuthHandler` simule un joueur par deux en-têtes (`factory.CreateClient(TestUser.Admin)`, `TestUser.Player`) pour les tests d'autorisation des routes ; **sans ces en-têtes, tout passe au vrai cookie** (validation comprise). `TestCertificate` fournit le certificat exigé en staging et en prod (`StagingSettings()`). Tests : `Players/GuestTests`, `Players/CookieValidationTests` (horloge simulée), `Players/LegacyCookieTests`, `Security/DataProtectionTests`, `UnitTests/Players`.

## Client Deezer (`InSeconds.Deezer`)

Projet à la racine de `src/back`, qui ne connaît ni l'API, ni `InSeconds.Infrastructure`, ni aucun module (vérifié par `ArchitectureTests/ProjectDependencyTests`). Le client Deezer, découpé en quatre ports **par besoin** :

| Port | Rôle | Résultat |
|---|---|---|
| `IPreviewProvider` | l'extrait audio d'un morceau (URL signée de 30 s), pour le jeu | `PreviewLookup` : `Found(url)`, `Missing` (réponse déterminée : pas d'extrait, ou morceau supprimé), `Unavailable` (quota, panne : l'état est **inconnu**) |
| `ITrackMetadataSource` | artiste, titre, pochette (hash), année de sortie, **rang Deezer** (`rank`), extrait : l'état réel chez Deezer | `TrackMetadataLookup` : `Found(DeezerTrack)`, `NotFound`, `Unavailable` |
| `IAlbumSource` | les **genres d'un album** (`/album/{id}` → `genres.data`) : le morceau n'a pas de genre chez Deezer, c'est l'album qui en porte | `AlbumLookup` : `Found(genres)` (liste vide si l'album n'en a aucun), `NotFound` (800 : album supprimé), `Unavailable` (même règle que pour les morceaux, piège 16 ; aussi une réponse **sans champ `genres`**, qui ne dit rien de l'album : il sera redemandé) |
| `ITrackSearch` | recherche par texte | `SearchLookup` : `Found(tracks)` (liste vide si rien ne correspond), `Unavailable` (quota, panne : l'échec est journalisé) ; un résultat sans identifiant est écarté |

- **Jamais de `null` ambigu** : trois cas explicites, et seul le premier ou le deuxième permet de conclure (piège 16 du CLAUDE.md racine).
- **Erreurs en HTTP 200** (piège 16) : Deezer renvoie quota (code 4), service occupé (700), morceau supprimé (800) dans un payload `{"error":{…}}` qui contourne la résilience HTTP. Le code **800** (« no data ») est une réponse déterminée (`Missing` / `NotFound`) ; tout autre code, connu ou futur, et toute erreur HTTP ou de lecture donnent `Unavailable`.
- **Jamais de `catch {}` nu** (piège 13) : `OperationCanceledException` est relancée **seulement si l'annulation vient de l'appelant** (`ct`) ; le délai d'attente interne d'un `HttpClient` lève la même exception et est un échec de Deezer (`Unavailable`, journalisé en `Warning`) ; le reste est journalisé en `Warning` (`DeezerLog`, EventId 1210 à 1217). **Jamais le texte d'une recherche dans les journaux** (piège 36) : seulement sa longueur (`QueryLength`).
- **Un seul `DeezerClient`** (`HttpClient` typé) implémente les quatre ports : un appel `/track/{id}` donne à la fois l'extrait, le rang, l'année, la pochette et l'**album** (`album.id`, `DeezerTrack.AlbumId`) (le contrôle nocturne n'a besoin que d'une requête par morceau). `release_date` donne l'année (**null si elle est inférieure à 1** : Deezer met « 0000-00-00 » pour une date inconnue), `rank` le rang, un morceau dont l'artiste ou le titre est vide ou blanc est « introuvable » (422 à l'ajout, jamais une exception de domaine donc une 500), le hash de pochette est extrait de `album.cover_medium`. **`GetTrackAsync` renvoie l'identifiant demandé**, pas le champ `id` de la réponse : c'est sur lui que le pool a vérifié les doublons, et une réponse sans `id` donnerait 0.
- **Cache** (`DeezerCache` : un `MemoryCache` **dédié**, 2000 entrées au plus, pas l'`IMemoryCache` partagé) : décorateurs des ports, pas le client.
  - **Pas de cache des extraits** : Deezer signe ses adresses pour 15 min (piège 14), un cache servirait des adresses presque expirées (l'ancien `CachedPreviewProvider`, avec sa marge d'1 h, ne gardait jamais rien : retiré le 17/10/2026, #279).
  - `CachedTrackSearch` : recherche en cache 1 h (clé : limite + texte rogné en minuscules), jamais un `Unavailable` ni une liste vide.
  - **Une `Size = 1` sur chaque `cache.Set`** (piège 24) : sans elle, `MemoryCache` avec une `SizeLimit` lève une exception à l'exécution (testé avec le vrai `DeezerCache`).
- **Enregistrement** (`AddDeezer(configuration)`, appelé par `ApiComposition` avant Wolverine) : `IPreviewProvider` (le jeu : Daily, par `ITrackPreviews` de Catalogue), `ITrackSearch`, `ITrackMetadataSource` et `IAlbumSource` sont le client **brut** (admin, ajout, actualisation, contrôle des extraits veulent l'état réel) ; la recherche publique demande le décorateur concret `CachedTrackSearch`. Ce sont des fabriques : `WolverineSetup` les déclare à `AlwaysUseServiceLocationFor` (`DeezerServiceCollectionExtensions.ServiceLocationTypes`), sinon `codegen write` refuse (service location interdite).
- **Réglages** : `Deezer:BaseUrl` (défaut `https://api.deezer.com`), `Deezer:ResilienceEnabled` (défaut `true`, `false` dans l'hôte de test et dans `ApiFactory` : une condition par configuration, jamais sur l'environnement). Avec la résilience : timeout 4 s par tentative, 15 s au total, nouvelles tentatives exponentielles (429, 5xx), coupe-circuit sur 30 s.
- **Faux** : `ReplaceDeezerHttpHandler(createHandler)` remplace le transport HTTP (le vrai client et le vrai cache tournent sur le faux). Cf. « Hôte de test ».
- Usage : **piège 47** du CLAUDE.md racine (conditions de l'API Deezer) : jamais d'audio ni de pochette Deezer stockés (le pool ne garde que le hash de la pochette) ni dans un cache persistant. La recherche publique ne renvoie que artiste et titre.
- Tests : `UnitTests/Deezer/DeezerClientTests` (les quatre ports, erreurs en 200, annulation, journaux sans la requête), `DeezerCacheTests` (TTL borné par la signature avec une horloge simulée, tailles, rien de mis en cache sur absence ou échec).

## Module Catalogue (`Modules/Catalogue/`)

Les morceaux du pool, leurs métadonnées Deezer, l'état de leur extrait, le pool admin. Point d'entrée `CatalogueModule.AddCatalogue()` (les endpoints Wolverine.Http sont découverts ; comme Players, pas de `MapCatalogue`).

- **Tables** (schéma `catalogue`, migrations `Catalogue` et `TrackGenres`) : `tracks` (`deezer_track_id bigint` unique `ix_tracks_deezer_track_id`, `artist`, `title`, `cover_hash`, `release_year smallint`, `deezer_rank`, `rank_updated_at`, `album_id bigint` (l'album chez Deezer), `genres_checked_at` (vide : les genres de l'album ne sont pas encore lus ; renseigné **même si l'album n'a aucun genre**), `preview_status smallint` 0 inconnu / 1 disponible / 2 absent avec un CHECK, `preview_checked_at`, `disabled_at`, `created_at`, `updated_at`), `genres` (`id` **celui de Deezer**, jamais généré, `name`) et `track_genres` (`track_id`, `genre_id`, clé composite, supprimée avec le morceau ou le genre : table de jonction déclarée par EF, sans entité propre). **`id` tiré d'une séquence HiLo** (`catalogue.tracks_hilo`, par 10, comme `device_sessions`) : l'endpoint d'ajout met l'identifiant dans sa réponse, construite avant l'enregistrement par Wolverine.
- **Domaine** (`Domain/`) : `Track` (constructeur privé, `private set`) : `Create(TrackMetadata, now)`, `Rename`, `Disable`/`Enable` (idempotentes), `RecordPreviewCheck(PreviewCheck, now)` qui **ne change rien sur `Unavailable`** (pas même la date du contrôle, piège 16) et renvoie si l'état a changé, `RecordRank`, `RecordAlbum` (un autre album remet les genres à lire), `RecordGenres` (remplace les genres et note la date de lecture, même sans genre), `ReplaceDeezerSource` (actualisation). `Genre` (identifiant de Deezer, nom, `Rename` si Deezer le change). `PreviewStatus` (valeurs stockées) et `PreviewCheck { Available, Missing, Unavailable }` (le résultat d'un contrôle, qui n'est pas un état). Aucune navigation vers un autre module ; le domaine ne connaît pas `InSeconds.Deezer` (`TrackMetadata` est son propre type, l'application traduit). `ICatalogueStore` (écritures et lectures préalables), `ICatalogueQueries` (lectures, `Application/`).
- **Contrats** (`Contracts/`, seul dossier que les autres modules peuvent utiliser) :
  - `TrackTitles.CleanDisplayTitle` : retire parenthèses et crochets (`Titre (Radio Edit)` → `Titre`), garde le titre entier s'il est entièrement entre parenthèses.
  - `ITrackUsage` (`Mode`, nom stable du mode, `GetAsync`) / `TrackUsage(LastUsedDate, UsageCount, UnlockDate, InTodayChallenge, UsedByMode)` : l'usage d'un morceau **par un mode de jeu**, que Catalogue ne connaît pas. `ITrackPoolUsage.GetByModeAsync` le rend mode par mode (`ModeUsage(Mode, Usage)`, seuls les modes concernés), `GetAsync` l'agrège. **Chaque mode ajoute sa propre implémentation** (`AddScoped<ITrackUsage>`, jamais `Replace`) ; Catalogue les agrège (`TrackPoolUsage`, exposé en `ITrackPoolUsage`, sans cooldown) : `IsUsed` (`UsageCount > 0 || UsedByMode`) est vrai dès qu'un seul mode le dit, supprimer ou actualiser un morceau utilisé répond 409 `catalogue.track_in_use`, et les dates et « défi du jour » combinent les modes (date la plus récente, apparitions additionnées). Le cooldown reste une règle du Daily : `IDailyTrackUsage` (Daily) ajoute `GetTracksInCooldownAsync(jour)`. `ITrackPoolUsage` est à `AlwaysUseServiceLocationFor` : le code généré le demande au conteneur, donc ajouter un mode **ne régénère pas** le code de Catalogue. Un mode qui n'a pas de cooldown répond `TrackUsage.None with { UsedByMode = true }`.
  - `ITrackDirectory` / `TrackInfo(Id, DeezerTrackId, Artist, Title, DisplayTitle, CoverUrl, ReleaseYear, DeezerRank, Genres)` : lecture des morceaux par Gameplay et Daily (nom de référence brut, titre affiché nettoyé, pochette reconstruite, noms des genres de l'album par ordre alphabétique).
  - `ITrackPreviews` : l'extrait des morceaux pour le jeu, demandé à Deezer à chaque appel (`IPreviewProvider`, sans cache, piège 14) ; `GetAsync` (un morceau) distingue extrait absent et Deezer indisponible (`PreviewAvailability`, piège 16), pour Runs.
- **Réglages** (`IOptionsMonitor`, relus à chaud) : `Catalogue:CoverUrlTemplate` (`infra.settings`, défaut `https://cdn-images.dzcdn.net/images/cover/{hash}/250x250-000000-80-0-0.jpg`, l'URL se reconstruit depuis `cover_hash`) ; `Catalogue:Refresh:BatchSize` (10) et `Catalogue:Refresh:BatchDelay` (1,5 s, relus au début de chaque contrôle, #319) : la cadence du contrôle (Deezer limite à ~50 requêtes / 5 s), réglables pour que les tests n'attendent pas.

il reçoit ceux du nouveau quand il est lu. **Un morceau désactivé n'est pas contrôlé** : désactivé avant sa première lecture d'album, il reste sans genre (sauf si un autre morceau du même album est lu) jusqu'à sa réactivation et le contrôle suivant ; sans effet sur le jeu. **À l'ajout** (`AddTrack`) : un appel `/album/{id}` de plus, écrit avec le morceau (`EnsureGenresAsync`, en EF : un genre déjà là est repris, les autres ajoutés avec la transaction du handler ; deux ajouts simultanés qui partagent un genre neuf se heurtent sur sa clé, le second est refusé en 409 `catalogue.concurrent_add`, la transaction de Wolverine étant alors annulée une nouvelle tentative n'y serait pas possible) ; un album indisponible n'empêche pas l'ajout, le contrôle nocturne rattrape. Le pool existant se rattrape à la première exécution (sur le staging, qui n'a pas de tâche planifiée : un lancement manuel depuis `/jobs`). `TrackInfo.Genres` (noms) les expose aux autres modules, `TrackListItem.Genres` à l'admin ; aucun mode ne s'en sert encore. Compte rendu lu par `GET /api/admin/jobs/last-runs` (témoin « Previews » de l'admin) : `result` = `{ "checked", "updated", "failed" }` (un dictionnaire : Hangfire n'écrit pas les propriétés à zéro d'un objet, `failed` serait absent). `[DisableConcurrentExecution(600)]` (le délai d'attente du verrou dépasse la durée d'un contrôle : la tâche de 23 h lancée pendant un contrôle lancé depuis `/jobs` attend qu'il finisse au lieu d'échouer), 2 nouvelles tentatives après 10 min si une exception sort (base). **Le handler est `[NonTransactional]`** : le contrôle dure plusieurs minutes (70 lots de 10 espacés de 1,5 s pour ~700 morceaux), une transaction Wolverine ouverte pendant les pauses retiendrait une connexion pour rien, et un seul enregistrement final perdrait tous les résultats si l'admin supprimait un morceau entre-temps (`DbUpdateConcurrencyException`). Les candidats sont lus **détachés** ; chaque lot est enregistré tout de suite par `ICatalogueStore.SaveRefreshedAsync` (un `ExecuteUpdate` par morceau, pas de `SaveChangesAsync` dans le handler) : un morceau supprimé entre-temps (0 ligne touchée) est ignoré, les autres lots sont gardés, et il n'est pas compté dans `updated` (`checked` compte tous les candidats vérifiés). Seuls l'état de l'extrait, le rang, l'album et `genres_checked_at` sont écrits (et les genres d'un morceau qui a changé d'album, retirés) : un renommage ou une désactivation faits pendant le contrôle ne sont jamais écrasés.
- **Rien n'est supprimé en cascade** : supprimer un morceau est refusé s'il a servi ; la clé étrangère `challenge_tracks.track_id → catalogue.tracks` (`RESTRICT`) est déclarée du côté de Daily.
- **Effet d'un renommage sur les réponses des joueurs** (verdicts déjà enregistrés conservés, les suivantes corrigées avec le nouveau nom, nom affiché changé pour tout le monde) : il vient de Daily, qui relit le nom à chaque réponse (`Daily/PlaySessionTests`, « renommage d'un morceau du défi du jour ») ; côté Catalogue, `PoolAdminTests` vérifie l'absence de verrou.
- **Tests** : `UnitTests/Catalogue` (`TrackTests` : états de l'extrait, `Unavailable` sans effet, renommage, désactivation ; `TrackTitlesTests` ; `SearchSuggestionsTests` ; `RefreshPreviewsHandlerTests` : le contrôle sans base, lots et espacement avec une horloge simulée ; `CatalogueSupportTests`), `IntegrationTests/Catalogue` (`SearchTests`, `PoolAdminTests` dont « renommer un morceau du défi du jour », `RefreshPreviewsTests` (tâche appelée directement), usage des morceaux simulé par `TestTrackUsage`), `Jobs/ScheduledJobsTests` (cron par défaut, `Never` en staging, les autres tâches décalées de 30 min), `Testing/CatalogueOpenApiTests`, 401/403 de toutes les routes par `Security/SecurityTests` (lues dans l'API).

## Module Daily (`Modules/Daily/`)

Le défi du jour. Point d'entrée `DailyModule.AddDaily()` (son `ITrackUsage` s'**ajoute** à ceux des autres modes, l'ordre d'enregistrement n'importe pas) : les défis, leur génération et l'usage des morceaux, les parties, le score, la série et les gels, les statistiques, les routes admin. Daily n'utilise de Catalogue que `Contracts`, et de Gameplay que `Contracts` (`ISeededShuffle`) ; Catalogue et Gameplay ne connaissent pas Daily (testé : `CatalogueEtGameplay_NeConnaissentPasDaily`, `Daily_NeDependQue…`).

- **Tables** (schéma `daily`, migration `Daily`) : `challenges` (`id` tiré d'une séquence HiLo `challenges_hilo`, `date` **unique** : `ix_challenges_date`, `seed`, `origin` : 1 nocturne, 2 à la volée, 3 admin, vide pour l'historique repris) et `challenge_tracks` (PK `(challenge_id, position)`, unique `(challenge_id, track_id)`, index sur `track_id` pour le cooldown, clé étrangère vers `catalogue.tracks` en `RESTRICT`). **La clé étrangère vers Catalogue est déclarée par le nom du type** (`HasOne("…Catalogue.Domain.Track", navigationName: null)`), pas par son type : Daily ne peut pas référencer le domaine de Catalogue. Aucune navigation entre modules, seulement des identifiants.
- **Domaine** (`Domain/`) : `DailyChallenge.Create(date, origine, morceaux)` (positions de 1 à N dans l'ordre du tirage, un morceau une seule fois, la graine est `DayNumber`), `ChallengeTrack`, `ChallengeOrigin`, `IDailyStore` (verrou de génération, lecture, ajout), `ITrackSelector` / `CooldownSeededSelector` (§ 5.3) → `TrackSelection(TrackIds, EligibleCount, Requested)`.
- **Tirage** (`CooldownSeededSelector`) : retire les morceaux en cooldown, **trie les candidats par identifiant** (le défi ne dépend ni de l'ordre rendu par la base, ni d'un doublon), puis Fisher-Yates à graine (`ISeededShuffle`) et garde les N premiers. Moins de N candidats : sélection vide, `IsSufficient` faux. Les candidats viennent de **`ITrackDirectory.ListPlayableIdsAsync`** (contrat de Catalogue) : non désactivés et extrait **disponible** (jamais « inconnu »), triés par identifiant.
- **Usage des morceaux** (`EfTrackUsage`, fourni en `IDailyTrackUsage` et en `ITrackUsage`) : **calculé** sur `challenge_tracks` + `challenges.date`, jamais stocké. `LastUsedDate` = dernier jour, `UsageCount` = nombre d'apparitions, `UnlockDate` = dernier jour + cooldown + 1 (le premier jour tirable), `InTodayChallenge` = apparu au jour de jeu en cours (`IGameCalendar`). **Bornes du cooldown** : un morceau tiré à une date ≥ jour − cooldown reste exclu (`LastUsedDate < jour − cooldown` pour être tirable). L'`UnlockDate` du pool admin est ce premier jour tirable. **Le cooldown suit la taille du pool** (#275, `Domain/TrackCooldown`, `Application/TrackCooldownPolicy`, recalculé à chaque appel) : ⌊ morceaux jouables (`ITrackDirectory.ListPlayableIdsAsync`) × `Daily:TrackCooldownPoolPercent` ÷ `Daily:TracksPerChallenge` ⌋ jours ; le pool ne bloque jamais plus de cette part, un petit pool a un petit cooldown (0 : un morceau peut revenir dès le lendemain). `GetTracksInCooldownAsync(jour)` sert aussi au contrôle nocturne des extraits (`catalogue-refresh`, qui demande demain).
- **Réglages** (`DailyOptions`, `IOptionsMonitor`, relus à chaud, aucune ligne en base nécessaire) : `Daily:TracksPerChallenge` (5, ne change que les nouveaux défis : la fin de partie compte les morceaux réels, piège 38) et `Daily:TrackCooldownPoolPercent` (75, de 10 à 90 : l'API refuse de démarrer au-delà, un réglage aberrant écrit à chaud retombe sur 75 ; remplace `Daily:TrackCooldownDays`, dont la migration `TrackCooldownPoolPercent` supprime la ligne).
- **Génération** (`GenerateDailyChallenge(Day, Origin)`, handler Wolverine, **une seule transaction**) : une seule logique pour la tâche de minuit, le secours à la volée (appelé par le démarrage d'une partie) et `/api/e2e/generate-today` de l'hôte de test. Étapes : **verrou consultatif** `pg_advisory_xact_lock(DAIL, numéro du jour)` (`IDailyStore.LockGenerationAsync`, refuse de tourner hors transaction) → défi déjà là : `AlreadyExists` sans rien changer → tirage → `Created`, ou `PoolInsufficient` sans rien écrire. **La course entre deux générations** (minuit et un joueur, par exemple) est donc réglée par le verrou : la seconde attend, voit le défi de la première et ne tire rien, sans passer par l'erreur de l'index unique ; testé avec un sélecteur lent (4 générations simultanées : une `Created`, trois `AlreadyExists`, un seul tirage) et deux jours différents qui ne s'attendent pas. Le résultat `GenerateChallengeResult` porte l'issue, le défi, le nombre de morceaux et ce qu'il manquait ; `ToReport()` en fait le compte rendu des tâches (`{ created, date, challengeId, tracks }`).
- **Tâches** (`IScheduledJob`, une ligne chacune, § 5.4 bis) :
  - `daily-generate-challenge` (`0 0 * * *`, UTC ; **tourne aussi en staging**, elle n'appelle pas Deezer, à `30 0 * * *` pour ne pas tomber en même temps que la prod sur le même VPS : entre minuit et 0 h 30, `POST /api/daily/sessions` y génère le défi à la volée) : génère le défi du jour de jeu en cours (`IGameCalendar.Today`), origine nocturne. **Un pool insuffisant lève `JobFailedException("admin.pool_insufficient")`** pour que Hangfire réessaie : `[AutomaticRetry(Attempts = 144, DelaysInSeconds = [600])]`, un essai toutes les 10 minutes pendant 24 h (le défaut de Hangfire s'arrête à 10 essais, 1 h 40 ; testé). `[DisableConcurrentExecution]`. Un défi déjà présent est un succès (`created: false`).
- **Lancement à la main** : depuis `/jobs` (tâche `daily-generate-challenge`, avec ses réessais). L'admin n'a pas de bouton : le témoin « Défi du jour » de l'onglet Actions lit le dernier passage par `GET /api/admin/jobs/last-runs`. L'origine « admin » ne sert plus qu'à `/api/e2e/generate-today`. Code d'erreur publié : `admin.pool_insufficient` (`DailyErrorCodes`, ne jamais le renommer).
- **Journal** (`DailyLog`, EventId 1300 à 1302) : défi généré (information), déjà présent (information), pool insuffisant (**erreur** : c'est ce qui doit alerter, et il se répète à chaque essai).
- **Tests** : `UnitTests/Daily` (`CooldownSeededSelectorTests` : tirage, déterminisme, ordre des candidats, doublons, cooldown, pool insuffisant ; `DailyChallengeTests`), `IntegrationTests/Daily` (`GenerateChallengeTests` : tirage, même défi pour la même graine, déjà présent, cooldown aux limites et réglage relu à chaud, morceaux désactivés / sans extrait / inconnus jamais tirés, pool insuffisant et regarni, nombre de morceaux réglable, **course entre générations**, tâches (compte rendu, exception, réessais), clé étrangère ; `TrackUsageTests` : usage calculé, limite du cooldown, jour de jeu, pool admin), `Testing/E2eHostTests` (seed par de vrais défis, `generate-today`), `Jobs/ScheduledJobsTests`, règles d'architecture.

### Parties

Les parties d'un joueur sur le défi du jour, leur score, sa série et ses gels. **Daily n'utilise des autres modules que leurs `Contracts`** : `Players/Contracts` (`ICurrentPlayer`, `IPlayerDirectory` : le joueur a-t-il un compte), `Catalogue/Contracts` (`ITrackDirectory`, `ITrackPreviews` : l'extrait des morceaux), `Gameplay/Contracts` (`TrackRound`, `HintPolicy`, `IHintProvider`, `IAnswerMatcher`). Les clés étrangères vers `players.players` sont déclarées **par le nom du type** (comme celle vers `catalogue.tracks`) : une **constante** portant ce nom compte comme une dépendance pour NetArchTest, le nom s'écrit en littéral ; et `InSecondsDbContext` applique les configurations de **Players et Catalogue d'abord** (EF ne retrouve une entité par son nom que si elle est déjà dans le modèle, sinon il en crée une autre sans erreur).

- **Tables** (schéma `daily`, migration `DailySessions`) : `sessions` (`id` tiré d'une séquence HiLo `sessions_hilo`, unique `(player_id, challenge_id)` : `ix_sessions_player_challenge`, index `(challenge_id, status)`, `status` 0 en cours / 1 terminée / 2 abandonnée / 3 expirée avec un CHECK, `current_position` / `current_listened_seconds` / `current_hint_level` : le verrou du morceau en cours, `freezes_used` / `freeze_earned` : l'effet de la complétion sur les gels), `answers` (PK `(session_id, position)` : une réponse par morceau, jamais deux ; `answered_at` vide pour l'historique repris) et `streaks` (`player_id`, `current_streak`, `last_played_date`, `freezes` ; pas de ligne = aucune série). **Le texte tapé par le joueur n'est jamais stocké** (ni journalisé) : seuls les verdicts (`artist_correct`, `title_correct`) le sont ; les colonnes `artist_answer` et `title_answer` ont été vidées puis supprimées (migration `DropTypedAnswers`, minimisation RGPD : rien ne les relisait).
- **Domaine** (`Domain/`) : `DailySession` (`Start`, `TurnOf(position, nombre réel de morceaux)`, `RoundOfCurrentTrack(politique)` qui reconstitue la `TrackRound` et **borne le niveau d'indice à la politique**, `KeepRound`, `Answer` qui libère le verrou et termine la partie sur le nombre réel de morceaux, `Abandon`, `Expire`), `SessionAnswer`, `DailyStreak` (`RecordCompletion(date du défi, compte lié ?, règles)`, `GrantAccountCreationFreeze`, `View` / `Compute` : la série effective d'un jour, protégée ou cassée, sans rien écrire), `IDailyScoringPolicy` / `DurationScoringPolicy` (barème), `TrackAnswerStats` (ce que la révélation montre des autres joueurs).
- **Réglages** (`DailyOptions`, `IOptionsMonitor`, relus à chaud) : `Daily:GuessTimerSeconds`, `AllowedDurationsSeconds`, `DurationScores` (liste d'objets `{ seconds, score }`), `HintUnlockDurationsSeconds`, `HintPenaltyPercent` (`{"1":30,"2":60}`), `StreakFreezeEveryDays`, `StreakFreezeMax`, `StreakLostNudgeMinDays`. **Aucune valeur initiale sur les listes et les dictionnaires** : le binder les AJOUTE aux éléments lus ; les défauts sont dans les propriétés `Effective…`. `DailyRules` (singleton) en tire à chaque appel la politique d'indices (bornée aux `IHintProvider` contigus depuis le niveau 1, repli sur les seuils par défaut si les siens ne sont pas croissants ; l'erreur au journal n'est écrite qu'une fois par valeur), les paliers (un palier que `numeric(4,2)` ne garderait pas tel quel fait retomber sur ceux par défaut), le barème, les paliers, les règles de gel ; `DailyOptionsStartupCheck` **refuse de démarrer** si les réglages sont incohérents (plus de niveaux d'indice que de fournisseurs, seuils non croissants, paliers ou pourcentages aberrants) : au démarrage seulement, un réglage changé à chaud ne fait pas tomber les parties en cours.
- **Routes** (`Application/`, Wolverine.Http en étapes `LoadAsync` / `Validate` / `Post`). Un morceau se désigne par sa **position** (1 à N). Le morceau en cours est toujours le premier sans réponse (piège 35).

| Route | Rôle |
|---|---|
| `GET /api/daily/settings` (public) | paliers, barème, `guessTimerSeconds`, `hints: [{ level, unlockSeconds, kind, penaltyPercent }]` (`kind` : `year`, `artistMasked`), règles de gel |
| `GET /api/daily/today` (public) | `{ state, tracksCount, completedCount, streak, completedGames, bestScore, yesterdayMedian }` : `no_challenge` / `can_start` / `resumable` / `already_played` / `abandoned`. Lecture seule : ne génère rien, ne crée ni joueur, ni cookie, ni partie. La série est celle d'**aujourd'hui**. `completedGames` : parties terminées du joueur (invité compris), tous jours confondus, 0 sans joueur : affichées par le panneau de série d'un compte (#283), et lues par le front pour le bandeau « crée un compte » d'un invité (ses 3 premières parties). `bestScore` : le record du joueur (meilleur score d'une partie terminée, tous jours, invité compris), vide sans partie terminée ; `yesterdayMedian` : le « score à battre » de l'accueil, la médiane des parties terminées d'hier (arrondie comme la page des jours passés), seulement pour qui n'a pas de record et à partir de 5 parties (`ScoreDistribution.MinPlayersForPercent`) ; jamais le meilleur score du jour |
| `POST /api/daily/sessions` (`[Authorize]`) | démarre ou **reprend** la partie du jour (réserve le joueur, expire ses parties d'un jour passé, **génère le défi à la volée** s'il manque). `{ sessionId, tracks: [{ position, previewUrl }], streak, isResuming, nextPosition, completedAnswers, currentTrack }`. **Ni artiste, ni titre, ni année, ni identifiant Deezer** (piège 31). 409 `daily.already_played` / `daily.abandoned`, 503 `daily.no_challenge` |

| `POST /api/daily/sessions/{id}/answers` | `{ position, listenedSeconds, wasExtended, artist, title }` → correction, `score`, le morceau (`correctArtist`, `correctTitle`, `deezerTrackId`, `coverUrl`), `hintLevelUsed`, `hintPenaltyPercentApplied`, les statistiques du morceau, `completed`. 400 `daily.listened_duration_below_verified_minimum` |
| `POST /api/daily/sessions/{id}/abandon` | 204 ; la partie ne se rejoue pas |

  Une partie d'un autre joueur répond 404 `daily.session_not_found` (rien n'en est révélé). Une partie qui n'est plus en cours : 409 `daily.already_played` (terminée) ou `daily.abandoned` (bouton ou expiration), et aussi une partie encore « en cours » sur un défi plus vieux que la veille (`SessionAccess.OldestPlayableDay` : la veille reste jouable après minuit, piège 18 ; au-delà, la photo du jour est figée). Un autre morceau que le morceau en cours : 409 `daily.already_answered`, 409 `daily.track_lock_not_released` (le verrou ne se déplace pas, piège 35), 404 `daily.track_not_found`.
- **Concurrence** : toute requête sur une partie la charge en `FOR UPDATE` (`IDailyStore.FindSessionForUpdateAsync`) : deux envois de la même réponse se suivent (l'un est enregistré, l'autre 409, jamais une 500). Le démarrage prend un verrou consultatif par joueur (`LockPlayerStartAsync`) : deux démarrages simultanés ne font qu'une partie, le second la reprend. `FindChallengeAsync(jour)` et `FindStreakAsync` regardent d'abord le contexte (un défi ou une série ajoutés plus tôt dans la même transaction ne sont pas encore en base).
- **Série** : lue puis écrite par la complétion et par le gel offert, sous un verrou consultatif par joueur (`LockStreakAsync`, avant `FindStreakAsync`) : deux créations simultanées de la ligne se suivent au lieu de se heurter sur la clé primaire.
- **Fin de partie** (`SubmitAnswerEndpoint.Post`, une seule transaction) : la réponse, le score, et, sur le dernier morceau **réel** du défi (piège 38), le statut, la série et les gels, **sur la date du défi** (piège 18). Les gels ne sont consommés ou gagnés que par un **compte** (`IPlayerDirectory`). Le gel offert à la création d'un compte (`DailyStreakGrants`, `IStreakGrants`) est accordé dans la transaction de la création : `max(stock, 1)`. Les droits RGPD d'un joueur passent par `IPlayerDataContributor` (`DailyPlayerData`, section `daily`) : la copie de sa série et de ses parties (artiste et titre lus par `ITrackDirectory`) et leur suppression, appelées par Players (cf. « Droits du joueur »).
- **Journal** (`DailyLog`) : **le texte du 1002 est lu par Grafana** (« morceau {id}) : palier … score … - morceau n°{position} : {artiste} / {titre} », #314), l'identifiant étant celui du morceau au catalogue (`{TrackId}`) ; le 1004 donne ce même identifiant et la position. Les chiffres du jeu dans Grafana viennent des compteurs (`DailyMetrics`, cf. « OpenTelemetry »), plus d'expressions régulières sur ces textes ; le tableau « Un joueur » filtre encore sur leur début (« Réponse de », « Indice niveau »…) : `UnitTests/Daily/DailyLogTests` fige les textes, **mettre le tableau à jour si l'un change**. Événements : 1000 partie démarrée, 1001 reprise, 1002 réponse (le morceau attendu, **jamais ce que le joueur a tapé**), 1003 terminée, 1004 indice, 1005 abandonnée ; 1304 défi généré à la volée, 1305 et 1306 réglages d'indice incohérents.
- **Wolverine** : un paramètre chargé par `LoadAsync` qui n'est pas le corps de la requête porte `[NotBody]` (sinon Wolverine tente de le lire dans le corps, 400 sans message) ; **un service concret** (`DailyRules`) aussi, quand il est le seul paramètre complexe après lui.
- **Tests** : `UnitTests/Daily` (`DailySessionTests`, `DailyStreakTests`, `DailyScoringAndRulesTests`, `TrackAnswerStatsTests`, `DailyLogTests`), `IntegrationTests/Daily` (`GameApi` : l'API, une horloge simulée, des joueurs par HTTP ; `StartSessionTests`, `PlaySessionTests`, `StreakTests`, `DailySettingsTests`), règles d'architecture.

### Statistiques

Les statistiques du jour, la photo figée des jours terminés et les stories hebdo. **Joueurs supprimés exclus partout** (R8) : Daily ne peut pas utiliser le type des joueurs (règle d'architecture), `Persistence/LiveData` joint `players.players` en SQL (`FromSql`, lecture seule, requête composable) et tout agrégat part de là, y compris `GetPriorAnswerStatsAsync` de la réponse.

- **Table** (schéma `daily`, migration `DailyDayStats`) : `challenge_day_stats` (`challenge_id` PK et clé étrangère vers `challenges` en cascade, `computed_at`, `version smallint`, `payload jsonb`).
- **Domaine** (`Domain/DayStats.cs`) : `DayStatsCalculator.Build` (pur : compteurs, scores, répartition, chiffres par morceau, joueurs ; `isPast` replie les parties « en cours » sur « expirées » ; paliers et barème **au calcul**, l'histogramme garde aussi les paliers écoutés qui ne sont plus dans le réglage ; **pas la pénalité d'indice** : rien n'y est calculé avec elle, les scores sont ceux enregistrés à chaque réponse, #319), `ScoreDistribution` (dix tranches, `BetterThanPercent`), `Medians` (entière pour `stats/today`, décimale pour la photo), `DayStatsPayload` (**version 1**, `DayStatsJson` en camelCase), `DayStatsSnapshot` (la ligne).
- **Lectures** (`IDailyStatsQueries`, `EfDailyStatsQueries`) : en **agrégats** (un `GROUP BY` par position, l'histogramme par palier), pas en lignes : `stats/today` est appelée par chaque joueur en fin de partie.

## Module Runs (`Modules/Runs/`)

Le second mode de jeu (Run, nom affiché « Platines », cf. [`docs/runs/`](../docs/runs/README.md)) : le défi, son tirage, les réglages, l'accès, la partie et la comparaison des joueurs d'une playlist. Schéma `runs`, point d'entrée `RunsModule.AddRuns()` (+ `AddRunsPlayerData()`). Daily et Runs ne se voient pas (`DailyEtRuns_NeSeVoientPas`) ; Runs n'utilise que les `Contracts` de Players, Catalogue et Gameplay (`Runs_NeDependQueDesContratsDesAutresModules_EtPasDeDeezer`).

- **`RunChallenge`** (agrégat immuable) : un défi = un code de 6 caractères (le lien partagé), une graine **jamais exposée**, des règles **figées à la création** (`RunRules` en `jsonb` : un changement de réglage ne touche que les défis à venir), ses morceaux rangés par manche (`RunChallengeTrack`, avec le multiplicateur de leur manche), `created_by` (nullable : un compte effacé n'efface pas le défi). `RunChallengeCode` : alphabet sans ambiguïté (`ABCDEFGHJKMNPQRSTUVWXYZ23456789`), tiré par `RandomNumberGenerator` ; `Normalize` accepte la saisie en minuscules.
- **`RunRules`** : `Rounds`, `TracksPerRound`, `ListenSeconds`, `ThresholdPercents` (jauge par manche), `MinMultiplier` → `MaxMultiplier` (interpolation linéaire de la première à la dernière manche, arrondie à 2 décimales).
- **Tirage** : `IRunTrackSelector` → `RankBandSelector` : les morceaux jouables sont triés par rang Deezer décroissant (sans rang = moins connu), découpés en autant de **tranches** que de manches (`n*(k-1)/rounds`), puis mélangés dans leur tranche (`ISeededShuffle`, graine + numéro de manche) : la difficulté monte de manche en manche. `RunChallengePlanner` lit le pool par `ITrackDirectory`, tire la graine, vérifie l'unicité du code avant insertion (5 essais).
- **Réglages `Runs:`** (`RunsOptions`, relus à chaud) : `Rounds` 4, `TracksPerRound` 5, `ListenSeconds` 10, `ThresholdPercents` `[40,50,60,70]`, `MinMultiplier` 1, `MaxMultiplier` 2, `Discs` (clés `runs.discs.*`). Contrôlés au **démarrage** (`RunsOptionsStartupCheck`, l'API refuse de démarrer) **et à l'usage** (`RunsRules.Current()` : une valeur incohérente écrite en base à chaud retombe sur les défauts, avec une erreur journalisée une fois par valeur, EventId 1400). Pas de valeur initiale sur les listes (défauts dans `Effective…`).
- **Accès sur invitation** (`runs.access`) : `IRunAccess` (Contracts) : `CanPlay(joueur)` est vrai pour un admin d'office, sinon pour un compte invité. Routes admin (policy Admin automatique) : `GET /api/admin/runs/access` (`listRunAccess`), `PUT` (`grantRunAccess`) et `DELETE /api/admin/runs/access/{playerId}` (`revokeRunAccess`, 204, idempotent) ; un invité ou un joueur inconnu : 404 `common.not_found`. Journaux : EventId 1401 (accordé), 1402 (retiré). Interrupteur dans l'onglet Joueurs de l'admin.
- **Données du joueur** : `RunsPlayerData` (`IPlayerDataContributor`, module `runs`) exporte ses parties, ses défis créés, son record et son accès, et les efface (record, parties et réponses, accès ; `created_by` mis à `null`) avant la ligne du joueur (piège 48). `RunsTrackUsage` (`ITrackUsage`, mode `runs`) répond `TrackUsage.None with { UsedByMode = true }` : un morceau d'un défi n'est pas supprimable et n'a pas de cooldown propre.
- **Partie** (`RunSession`, statut `Pending` / `Won` / `Lost` / `Abandoned`) : **le morceau en cours est le premier sans réponse** (verrou, `TurnOf` comme au Daily, piège 35) ; `RoundOfCurrentTrack` / `KeepRound` gardent l'écoute (`TrackRound` de Gameplay, sans indice ; l'écoute est fixe, la réponse annonce toujours `ListenSeconds`). `Answer` note les points (`IRunScoringPolicy` → `ArtistTitleScoring` : (50 + 50) × multiplicateur, arrondi au plus proche sur le total du morceau), libère le verrou et, au dernier morceau d'une manche, compare son score à l'objectif (`RunGauge` : pourcentage figé × maximum de la manche, arrondi au plus proche, `>=`) : manche suivante, `Lost`, ou `Won` après la dernière ; fin sur le nombre **réel** de morceaux du défi (piège 38). Jauge pleine avant la fin : les morceaux restants se jouent. Disque : `DiscLadder` (manches passées → clé `runs.discs.*`, étoiles au-delà de la liste). Record (`RunRecord`, meilleur score et meilleur disque) mis à jour dans la transaction de fin d'une partie gagnée ou perdue, sous `pg_advisory_xact_lock` par joueur ; une partie abandonnée ne compte pas.
- **Morceau sans extrait : neutralisé par le serveur**, jamais sur demande du client. `RunPlayer.AdvanceAsync` (après un démarrage, une reprise, une réponse ou `POST …/preview`) demande l'extrait du morceau en cours par `ITrackPreviews.GetAsync`, qui distingue `Available`, `Missing` (réponse déterminée) et `Unavailable` (panne, quota, piège 16). `Missing` : `RunSession.Neutralize` enregistre une réponse `neutralized` à 0 point, le morceau sort du maximum de sa manche (l'objectif se recalcule : 200 → 160 en manche 1), et la recherche passe au suivant (une manche entièrement neutralisée est passée, objectif 0). `Unavailable` : le morceau reste en cours, `previewUrl` vide, le joueur réessaie par `POST …/preview`. Journaux : EventId 1407 (neutralisé), 1410 (indisponible).
- **Routes** (`RunEndpoints.cs`, `LoadAsync` / `Validate` / `Post`, transaction Wolverine) : `GET /api/runs/me` (`getRunsMe`, anonyme permis, ne crée rien : `hasAccess`, record, partie en cours) ; `POST /api/runs/challenges` (`launchRun` : accès requis, sinon 403 `runs.access_denied` ; verrou de démarrage par joueur ; tire la playlist et crée la partie de son auteur ; 503 `runs.no_challenge` ; limite `run-launch`, 20 par joueur en 10 min) ; `GET /api/runs/challenges/{code}` (`getRunChallenge`, anonyme permis, code insensible à la casse : pseudo de l'auteur, morceaux, manches, écoute, `myStatus` `none` / `pending` / `won` / `lost` / `abandoned` ; aucun morceau ; 404 `runs.challenge_not_found` ; limite `run-link`, 60 par IP en 5 min) ; `POST /api/runs/challenges/{code}/sessions` (`joinRun` : relève ou reprend, sans accès demandé ; 409 `runs.already_played` / `runs.abandoned`) ; `GET /api/runs/sessions/{id}` (`getRunSession`, lecture seule, sans Deezer) ; `PATCH …/listening` (`updateRunListening`, 400 au-delà de l'écoute fixe) ; `POST …/preview` (`refreshRunPreview`) ; `POST …/answers` (`submitRunAnswer`, artiste et titre vides : passer) ; `POST …/abandon` (`abandonRun`, 204) ; `GET /api/runs/challenges/{code}/comparison` (`getRunComparison`, `RunComparison.cs`, `[Authorize]`, limite `run-link`) : les parties **gagnées ou perdues** de la playlist, une ligne par partie (pseudo, vide pour un invité ; disque et étoiles ; le score de chaque manche, vide pour une manche non jouée ; total ; `isMe`), triées par total (à égalité : plus de manches passées, puis la première terminée), avec le pseudo de l'auteur et le nombre de joueurs ; **que des scores, jamais un morceau** (piège 31). Fermée tant qu'on n'a pas fini sa propre partie : 409 `runs.comparison_locked` (pas de partie, ou en cours) ; une partie abandonnée y a accès (finie) sans figurer au tableau ; 404 `runs.challenge_not_found`, 401 sans identité. La partie d'un autre : 404 `runs.session_not_found`.
- **Réponses** (`RunsResponses.cs`, dictées par les écrans, `docs/runs/conception.md` § 3.5) : `RunPlayResponse` (démarrage, reprise, extrait, réponse) = `session` (`RunSessionResponse` : manche en cours avec score, objectif et maximum, pastilles de la manche, ou `finish`), `revealed` (le morceau répondu : artiste, titre, pochette, identifiant Deezer, verdicts, points), `neutralized` (position, manche, objectif avant et après), `roundSummaries` (bilan des manches qui viennent de finir), `current` (le morceau à jouer, avec l'extrait **de ce seul morceau**, piège 31), `isResuming`. `RunFinishResponse` : statut, disque, score, manches passées, morceaux trouvés sur le total, chaque morceau joué, score et objectif de chaque manche (vides si non jouée), record (`isNew` : cette partie l'a établi), code de la playlist. Un morceau neutralisé ne dit rien de lui.
- **Métriques** (`RunsMetrics`, meter `InSeconds.Runs`) : `inseconds.runs.sessions` (`event` : `launched`, `joined`, `won`, `lost`, `abandoned`), `inseconds.runs.answers` (`round`, `artist_found`, `title_found`), `inseconds.runs.neutralized`, `inseconds.runs.discs` (`disc`). Journaux 1403 à 1411 (`RunsLog`), jamais le texte saisi.
- **Tables** : `challenges` (`code char(6)` unique), `challenge_tracks` (PK `(challenge_id, position)`), `sessions` (unique `(challenge_id, player_id)`, statut 0 en cours / 1 gagnée / 2 perdue / 3 abandonnée), `answers` (PK `(session_id, position)`, jamais le texte saisi), `records`, `access`. Clés étrangères déclarées par le nom du type, identifiants seulement vers les autres modules.
- **Erreurs** : `RunsErrorCodes` (`runs.*`, ne jamais renommer un code publié), `RunsProblems` ; `runs.comparison_locked` est celui de la comparaison.
- **Tests** : `UnitTests/Runs` (`RankBandSelectorTests`, `RunRulesTests`, `RunChallengeTests`, `RunsOptionsTests`, `RunSessionTests` : verrou, jauge, arrondis, neutralisation, disques, record), `IntegrationTests/Runs` (`RunPlayTests` : partie gagnée, perdue, abandonnée, ami, verrou, neutralisation, Deezer indisponible, réglage changé en cours de partie, double démarrage, journaux ; `RunRateLimitTests`, `RunsMetricsTests`, `RunComparisonTests` (verrouillée avant la fin, à plusieurs joueurs, manches non jouées vides, égalités, abandon et en cours absents du tableau), `RunAccessTests`, `RunChallengeTests`, `RunsPlayerDataTests`, `RunsTrackUsageTests`, `RunsSettingsTests` ; `RunGame` joue par HTTP), `Testing/RunsOpenApiTests`, `PlayerDataTests` (section `runs` de l'export).

## Module Gameplay (`Modules/Gameplay/`)

La mécanique d'un morceau, partagée par les modes : **de la logique pure, sans table, route ni réglage**. Point d'entrée `GameplayModule.AddGameplay()` (singletons : `IAnswerMatcher`, `ISeededShuffle`, un `IHintProvider` par niveau). Ne dépend d'aucun autre module (au plus de `Catalogue/Contracts`, permis) et reste sans accès aux données ni au web : testé par `ArchitectureTests` (`Gameplay_NeDependQue…`, `LesModulesDesNoyaux_NeDependentPasDeGameplay`). **Tout ce qu'un mode utilise est dans `Contracts/`** (un mode n'utilise d'un autre module que ses contrats) ; `Domain/` ne contient que les implémentations.
- **`TrackRound`** (objet valeur immuable, `Contracts/`) : ce que la manche garde, **ni le morceau ni les points**. `Start`, `Resume(listenedSeconds, hintLevel)` (le mode range ces deux nombres dans sa session et reconstitue la manche : Daily, `current_listened_seconds` et `current_hint_level`), `Listen(seconds)`, `RevealHint(level, policy)`, `Answer(claimedSeconds, artist, title, expected, matcher)`. Identité du morceau et verrou (piège 35) : l'affaire du mode.
  - **Plancher d'écoute** (piège 35) : `Listen` garde le **maximum** (écouter moins, rejouer, recharger la page ne le réduit jamais). `Answer` **refuse** (`AnswerResult.BelowFloor(plancher)`) un palier annoncé inférieur au plancher : écouter longuement ou débloquer un indice puis annoncer un palier court pour gagner plus. Un morceau sans extrait (palier 0, jamais écouté) n'a pas de plancher.
  - **Indices** : `RevealHint` refuse un niveau que la politique du mode ne propose pas (`UnknownLevel`) ou dont le seuil n'est pas atteint (`NotUnlocked`, avec `UnlocksAtSeconds`). Le niveau garde son **maximum** (redemander un niveau plus bas est accepté, rien ne redescend) ; **écouter plus ne révèle rien et ne remet rien à zéro** (seul le clic explicite révèle, et ce qui est révélé reste). Le niveau d'indice n'est jamais fourni par le client : il vient de la manche, que le mode relit de sa session.
  - **`RoundOutcome`** : `ArtistCorrect`, `TitleCorrect` (corrigés séparément, le score partiel du mode en dépend), le palier annoncé et le niveau d'indice révélé ; `FoundBoth`, `FoundAny`. **Aucun point** : le calcul appartient au mode (`IDailyScoringPolicy` de Daily).
- **`HintPolicy`** (propre à chaque mode) : les durées d'écoute qui débloquent les niveaux (`new HintPolicy([5m, 10m])`), **strictement positives et croissantes** (refusé sinon). `HintPolicy.None` : un mode sans indice. Daily la construit de ses réglages (`DailyRules`).
- **`IHintProvider`** (un par élément révélé) : `YearHint` (niveau 1, année, valeur `null` si inconnue, format invariant) et `HangmanArtistHint` (niveau 2, artiste « pendu » : première lettre de chaque mot, lettres et chiffres masqués, ponctuation gardée, mots séparés par 3 espaces ; un nom sans mot donne un motif vide). `HintFacts.UpTo(level, providers, subject)` : **cumulatif** (le niveau 2 rend aussi l'année), dans l'ordre des niveaux. Un indice de plus (décennie, genre) = un fournisseur de plus, sans toucher à `TrackRound`.
- **`FuzzyAnswerMatcher`** (`IAnswerMatcher`, ex-`TextNormalizer`) : insensible à la casse, aux accents, aux parenthèses et crochets, à la ponctuation et aux mots vides (`the le la les un une de du des and et feat ft vs`), puis distance de Levenshtein ≤ **min(2, longueur de la référence ÷ 3)** (moins de 3 caractères : égalité stricte ; 3 à 5 : une faute) : calculée sur la **référence**, pas sur la saisie (l'allonger ne gonfle pas la tolérance). `FuzzyAnswerMatcher(maxTypos)` pour une autre tolérance. Autres règles : une saisie de plus de 600 caractères (`MaxInputLength`, le double des limites de l'API) est refusée sans être lue (coût quadratique sur des « ( » non fermées), et la distance n'est pas calculée quand l'écart de longueur dépasse déjà le seuil. Une référence faite de mots vides (« The The ») se normalise en chaîne vide et n'est égalée que par une saisie qui se normalise pareil.
- **`FisherYatesShuffle`** (`ISeededShuffle`) : Fisher-Yates à graine, **ordre stable** pour une même graine et une même liste (testé contre un ordre épinglé : changer l'algorithme changerait les morceaux d'une date déjà annoncée). La liste reçue n'est pas modifiée. `Random(graine)` est voulu : la graine est publique (le numéro du jour), tout le monde joue le même défi.
- **Tests** (`UnitTests/Gameplay`, 134 tests) : correction (cas limites, accents, ponctuation, mots vides, seuil par longueur, tolérance configurable, cas vides), manche (plancher, indices, cumul, politique, correction, parcours « écouter plus après un indice »), indices (année, pendu, cumul, politique de déblocage), tirage (déterminisme, permutation, pas de biais de position, ordre épinglé).

## Document OpenAPI (hôte de test seulement)

Le front génère un client NSwag **par module** à partir d'un document OpenAPI. Ces documents ne sont servis que par `InSeconds.Api.Testing` (jamais par l'API de prod, S9 : `Microsoft.AspNetCore.OpenApi` n'est référencé que par le projet de test, `OpenApiTests` vérifie le 404 sur l'API) : `GET /openapi/players.json`, `GET /openapi/catalogue.json`, `GET /openapi/daily.json`, `GET /openapi/runs.json` (`api/runs` et `api/admin/runs`) et `GET /openapi/admin.json` (les témoins des tâches, `getJobLastRuns`, `api/admin/jobs`, qui n'est pas un module) (`ApiDocs/OpenApiDocuments`, un `AddOpenApi` par module filtré sur le ou les préfixes de ses routes : `api/players` ; `api/catalogue` et `api/admin/catalogue` ; ajouter un module = ajouter un `AddModuleDocument`).

- **Contrat porté par les endpoints** : `OperationId` de l'attribut Wolverine (Players : `createGuest`, `getMe`, `requestMagicLink`, `verifyMagicLink`, `updatePseudo`, `requestEmailChange`, `confirmEmailChange`, `logout`, `listDevices`, `revokeDevice`, `revokeOtherDevices`, `exportMyData`, `deleteMyAccount` ; Catalogue : `searchTracks`, `listTracks`, `addTrack`, `renameTrack`, `updateTrack`, `setTrackDisabled`, `deleteTrack`, `searchDeezer`) et `[ProducesResponseType<ProblemDetails>(…)]` pour les erreurs 401/403/404/409/429 (le 400 de validation est déduit par Wolverine). `GET /api/players/me` : 200 et 204. Ces attributs ne changent ni le comportement ni le code Wolverine généré.
- **Nettoyage par l'hôte de test** (transformers) : un seul tag par module (`Players` : un seul `PlayersClient` ; `Catalogue`), ni titre ni description déduits de la route, pas de serveur, entiers en `integer` (un entier nullable, comme `releaseYear`, reste `integer | null`, sauf le `status` d'un `ProblemDetails`, que le client des joueurs a déjà généré en nombre), propriétés nulles d'un corps de requête facultatives (`pseudo`), pas de corps sur les 204, et suppression du 404 sans schéma que Wolverine déclare partout (seuls les 404 `ProblemDetails` déclarés restent).
- **Documents sauvegardés** : `InSeconds.Api.Testing/openapi/players.json`, `openapi/catalogue.json`, `openapi/daily.json` et `openapi/admin.json` (celui de Daily : préfixes `api/daily` et `api/admin/daily`, avec le tableau de bord, les stats par défi, l'historique, l'historique d'un joueur, le réglage du cooldown, et un troisième préfixe `api/admin/players`, la liste des joueurs inscrits, servie par Daily ; un transformer fait des **décimaux** des `number` (durées en secondes, moyennes), sans le « nombre ou texte » avec motif que .NET décrit par défaut ; les documents des joueurs et du catalogue n'en ont pas, ils ne changent pas ; `DailyOpenApiTests`), sources des clients du front. `OpenApiTests` et `CatalogueOpenApiTests` (`Le_document_sauvegarde_pour_le_front_est_a_jour`) échouent s'ils sont périmés. Les régénérer après tout changement d'un endpoint du module : lancer l'hôte de test (`ASPNETCORE_ENVIRONMENT=Testing`, base PostgreSQL dans `ConnectionStrings__DefaultConnection`, `dotnet run --no-launch-profile --project InSeconds.Api.Testing --urls http://localhost:5177`), puis enregistrer `GET /openapi/<module>.json` indenté (2 espaces) dans le fichier du module. Une base jetable suffit : `docker run -d --name pg -e POSTGRES_PASSWORD=x -p 55434:5432 postgres:17-alpine`. Sous Windows, `OpenApi/` et `openapi/` sont le même dossier : le code est dans `ApiDocs/`, les JSON dans `openapi/`.

## Erreurs du front (`POST /api/client-errors`)

`Infrastructure/Errors/ReportClientErrorEndpoint.cs`, contrat (`source` `js`/`http`/`csp`, `message`, `stack`, `url`, `httpStatus`, `relatedTraceId`) plus `appVersion` (date de build du front, ≤ 40) et `online` (`navigator.onLine`), facultatifs, appelé par `ErrorReportingService` du front (via `HttpBackend`, hors client généré : `[ExcludeFromDescription]`).

- `source: "csp"` : gardée pour un front encore en cache ; les violations de la CSP passent désormais par `POST /api/csp-reports` (ci-dessous).
- Public, limité par IP (`[EnableRateLimiting(RateLimitPolicies.ClientErrorReport)]`, 20 / 5 min), bornes du validator (message ≤ 1000, pile ≤ 8000, URL ≤ 500, statut 0-599, trace ≤ 64). Réponse 204 (`[EmptyResponse]`, pas d'`IResult`).
- Journalisé en **Error**, EventId **1100** et message stable (`ClientErrorLog`) complété par `version {AppVersion}, en ligne {Online}, appareil {Device}` : les tableaux de bord existants (filtre « Erreur front ») restent valables. `Device` = `DeviceLabel` du `User-Agent` de la requête (« Safari · iPhone »), **jamais l'en-tête brut**. Retours à la ligne neutralisés (pile aplatie avec `|`), **query string et fragment retirés de l'URL côté serveur** même si un client en envoie. Le `PlayerId` du joueur est posé par `PlayerTelemetryMiddleware` (cf. « Identité du joueur dans la télémétrie »).
- Tests : `UnitTests/Infrastructure/ReportClientErrorTests` (validation, journal, version/connexion/appareil, rapport sans ces champs), `IntegrationTests/ClientErrorTests` (204, version/connexion/appareil journalisés sans le `User-Agent` brut, 400 ProblemDetails, 429 au 21e rapport ; confidentialité : un cookie, un `Authorization` et un jeton dans l'URL n'apparaissent ni dans les traces ni dans les journaux, test `Traces_NeContiennentNiCookieNiAuthorization`).


### Violations de la CSP (`POST /api/csp-reports`)

`Infrastructure/Errors/ReportCspViolationEndpoint.cs` : rapports envoyés par le navigateur lui-même (directives `report-to` et `report-uri` de `nginx/csp.conf.template`), dès le chargement de la page. `CspReportParser` lit les deux formats sans se fier au `Content-Type` : Reporting API (`application/reports+json`, tableau de rapports `type: "csp-violation"`, `body` en camelCase) et ancien `report-uri` (`application/csp-report`, objet `csp-report` en kebab-case ; Safari n'envoie que `violated-directive`, dont on garde le premier mot).

- Public, sans cookie (le navigateur n'en envoie pas : pas de `PlayerId`), limité par IP (`RateLimitPolicies.CspReport`, 30 / 5 min), corps lu jusqu'à 64 Ko (au-delà : ignoré), 10 violations au plus par requête, champs tronqués à 500 caractères, violations d'une extension du navigateur écartées (`chrome-extension:`, `moz-extension:`, `safari-web-extension:`…). Toujours 204 (`[EmptyResponse]`), même pour un rapport illisible : le navigateur ne lit pas la réponse.
- Journalisé par `ClientErrorLog` (EventId 1100), source `csp`, URL = chemin de la page seul, message `CSP (report|enforce) <directive> bloque <ressource> depuis <fichier>:<ligne>` sans query string : la tuile « Violations CSP » (filtre `Erreur front (csp)`) n'a pas changé.
- Tests : `UnitTests/Infrastructure/CspReportParserTests`, `IntegrationTests/CspReportTests`.

## Staging

`docker-compose.staging.yml` (racine du dépôt) construit cette API (`InSeconds.Api/Dockerfile`) et le front, en `ASPNETCORE_ENVIRONMENT=Staging`, sur la base `inseconds_staging` (un schéma par module). `deploy/vps/deploy.sh staging` (même script que la prod, cf. `docs/exploitation/deploiement.md`) :

1. vérifie le certificat Data Protection (`secrets/dataprotection.pfx` à la racine du checkout du VPS, monté en lecture seule sur `/run/secrets/dataprotection.pfx`) : présent, et lisible par l'utilisateur de l'image (`app`, uid/gid **1654**) ;
2. applique les migrations dans un conteneur jetable (`--migrate-only`), **avant** de remplacer les conteneurs ;
3. redémarre l'API (Wolverine et Hangfire créent leurs schémas à ce moment) et le front ;
4. lance `deploy/vps/smoke-test.sh` sur `https://api-dev.inseconds.cc` : `/api/e2e/reset` et `/api/auth/dev-login` en 404 (S9, sondés en GET : présents, ils répondraient 405 sans rien exécuter), en-têtes de sécurité (S15), `/jobs` en 401/403 ou derrière Cloudflare Access (S3).

**Certificat Data Protection** : lu par l'API (`ProtectKeysWithCertificate`, S16, cf. « Authentification »), sous les clés `DataProtection:CertificatePath` (`/run/secrets/dataprotection.pfx`) et `DataProtection:CertificatePassword` (`DATA_PROTECTION_CERTIFICATE_PASSWORD` de `.env.staging`, obligatoire : compose refuse de démarrer sans).
